## 1. 목적

내가 해온 프로젝트와 문제 해결 경험을 기억하고, 그 기억과 웹 검색·모델 지식을 결합해
**약점을 보완하고 다음에 배울 것을 제시하며 지속적으로 대화하는 개인 AI 어시스턴트**를 만든다.
첫 번째 역할은 튜터다.

### 학습 목표 (우선순위 순)

| 트랙 | 내용 | 초기 가중치 |
|---|---|---|
| JS/TS | 언어 이해(코드를 빨리 읽고 리뷰하기), JS 생태계(모듈·패키지·빌드 도구·런타임). 코딩테스트는 직접 풀어 보는 편이 나아 다루지 않는다 | 0.2 |
| 관계형 DB | 데이터 모델링·ERD·정규화, SQL, 인덱스와 쿼리 최적화, 트랜잭션, DB 내부 구조 | 0.2 |
| 백엔드 | 공통 서버 설계, NestJS와 Spring의 작동 방식과 사용법 | 0.2 |
| IT 인프라 | 운영체제에서 컨테이너까지(인프런 "Docker가 쉬워지는 운영체제 이야기" 커리큘럼) | 0.2 |
| 네트워크 | IP·TCP·DNS, HTTP, TLS, 프록시 등 웹 서비스가 통신하는 원리 | 0.2 |
| MCP와 이 서버 설계 | MCP 스펙, 모델이 도구를 쓰는 방식, 이 서버의 설계 결정과 트레이드오프, 확장·성능 개선 지점 | 0.2 |

- 1순위는 지금 업무 실력이다(ADR-0022). 시드 개념은 앞으로 배울 커리큘럼이고, 이미 아는 것은 학습 기록과 수집이 채운다.
- 수집한 경험의 프런트엔드 개념은 JS/TS, GIS 개념은 관계형 DB 트랙에 둔다. 여러 경험에 다시 쓰일 일반 개념만 받고, 시드 커리큘럼에는 넣지 않는다. 운영 경험은 IT 인프라 시드의 상위 개념(CI/CD 파이프라인, 배포 전략, 리눅스 서버 운영) 아래로 묶는다(ADR-0025).
- 업무 경험에서 나온 판단 원칙은 이 트랙들의 개념에 연결하고, 회사 맥락을 걷어낸 상황 판단형 객관식으로 묻는다(ADR-0021, 7.3).
- 개념 하나는 트랙 하나에만 속한다. 네트워크는 "프로토콜이 어떻게 동작하나", IT 인프라는 "리눅스에서 어떻게 구성되고 진단하나"를 맡는다. 트랙에 걸친 관계는 개념 간선으로 잇는다.

장기 방향: 프론트엔드와 백엔드를 아우르는 풀스택 개발자.

### 성공 기준

- Claude 앱에서 튜터링 대화와 복습을 이어갈 수 있다. 처음에는 맥미니의 Claude Desktop에서 직접 시작하고, 먼저 말 걸기(4단계)와 원격 전환(5단계) 뒤에는 아침 복습·저녁 주제를 모바일·아이패드에서도 받는다.
- 튜터가 대화와 문제에서 내 실제 경험(Notion)을 근거로 연결한다.
- 개념별 숙련도와 약점이 객관적인 풀이 기록으로 추적되고, 주간 리포트로 변화가 보인다.
- 모든 LLM 사용이 Claude 구독(Claude 앱, `claude` CLI)으로 동작한다. API 키를 사용하지 않는다.

## 4. 아키텍처

맥미니에서 실행하는 **NestJS 애플리케이션**(모듈러 모놀리스)과 Docker로 띄우는 **PostgreSQL 16**으로 구성한다. 같은 코드에 진입점을 둘 둔다.

- **MCP 진입점(stdio):** Claude Desktop이 필요할 때 띄운다. 도구 호출을 받아 유스케이스를 실행한다.
- **상시 실행 진입점:** launchd 사용자 에이전트(`ops/install.sh`)가 띄우고 죽으면 다시 띄운다. 원격 서버인 MCP HTTP 진입점(`mcp-http.ts`)이고, 서버 예약 작업(새벽 준비, 학습 알림)도 같은 프로세스의 스케줄러가 돌린다(ADR-0035·0036). 아래 그림의 "상시 실행 진입점"이 이 프로세스다.

```
맥미니
┌────────────────────────────────────────────────────────────────┐
│ Claude Desktop (대화)                                             │
│        │ stdio                                                  │
│        ▼                                                        │
│ [MCP 진입점] 도구 처리기 ─┐      [상시 실행 진입점] 서버 예약 작업 ─┐ │
│                         ▼                                   ▼ │
│   ┌──────────────── core ────────────────┐                     │
│   │ mcp          도구 등록, 처리기 탐색     │                     │
│   │ memory       경험 카드, 원문 문서·청크   │                     │
│   │ knowledge    개념 그래프, 트랙           │                     │
│   │ ingestion    Notion 수집, 증분 동기화     │                     │
│   │ llm          ClaudeCliClient           │                     │
│   │ scheduler    예약 작업, 놓친 실행 복구    │                     │
│   ├──────────────── tutor ───────────────┤                     │
│   │ study        학습 맥락 조회, 학습 기록    │                     │
│   │ quiz         출제, 검증, 채점            │                     │
│   │ mastery      FSRS, 숙련도, 약점 지도     │                     │
│   │ outreach     아침 복습, 저녁 주제, 주간 리포트│                  │
│   └──────────────────────────────────────┘                     │
│             │                     │                            │
│             ▼                     ▼                            │
│      claude -p 서브프로세스      PostgreSQL (Docker)              │
│      (백그라운드 작업만)                                          │
└────────────────────────────────────────────────────────────────┘

### 원칙

- 모든 상태는 PostgreSQL에 둔다. 대화 내용은 Claude 앱에 남고, 서버에는 도구로 기록된 것만 남는다.
- **계산은 코드로, 생성과 대화는 LLM으로.** 스케줄링, 숙련도, 약점 점수, 채점 반영은 코드가 결정적으로 계산한다. Claude 앱은 대화를, `claude -p`는 추출·출제·검증·오개념 태깅을 맡는다(서술형을 만들면 서술형 채점도).
- **서버가 정답을 지킨다.** 도구 결과에 아직 풀지 않은 문제의 정답·채점 기준을 싣지 않는다. 답은 `submit_answer`로 받고 서버가 채점한다.
- `claude -p` 호출은 반드시 `ClaudeClient` 인터페이스(구현: `ClaudeCliClient`)를 거친다.
- MCP 도구 처리기는 MCP SDK 객체를 유스케이스에 넘기지 않고, 전송 방식(stdio·HTTP)을 모른다. 원격 전환 때 Streamable HTTP 진입점만 추가한다.
- 도구는 읽기와 학습 기록만 둔다. 삭제처럼 되돌릴 수 없는 도구는 만들지 않는다.
- 향후 `career` 모듈(이력서·포트폴리오, Canva 연동)이 `core`의 기억을 공유할 수 있도록 모듈을 `core` / `tutor`로 분리한다 (ADR-0015).

### 모듈 구조 (초안)

```
src/
├── mcp-stdio.ts     # MCP 진입점 (Claude Desktop이 띄움)
├── mcp-http.ts      # MCP HTTP 진입점, Nest HTTP 앱 (/mcp, /healthz, 원격 커넥터의 바탕, 4단계), 예약 작업 (5단계)
├── core
│   ├── mcp          # MCP 서버, 도구 등록, 도구 처리기 탐색, /mcp 컨트롤러
│   ├── health       # /healthz 컨트롤러
│   ├── llm          # ClaudeClient, ClaudeCliClient, 프롬프트 템플릿, 호출 로그
│   ├── memory       # SourceDocument, DocumentChunk, Experience, DecisionCase
│   ├── knowledge    # Track, Concept, ConceptEdge, ConceptGraphRepository
│   ├── ingestion    # Source 인터페이스, NotionSource, 동기화 서비스
│   └── scheduler    # 매일 예약 작업, 실행 기록, 놓친 실행 따라잡기, 잠금
└── tutor
    ├── study        # 학습 맥락 조회, 학습 기록 도구, 서버 instructions
    ├── quiz
    ├── mastery
    └── outreach
```

`quiz` 모듈은 안을 `domain/`·`application/`·`infrastructure/`·`presentation/` 레이어 폴더로 나눠 시도한다(ADR-0020). 다른 모듈은 파일 이름 접미사로 역할을 구분한다(ADR-0015).

기능 모듈의 MCP 도구 처리기는 그 기능의 `mcp/` 폴더(`quiz`는 `presentation/mcp/`)에 두고, `core/mcp`가 데코레이터 탐색으로 모아 등록한다(`core`는 `tutor`를 import하지 않는다).

stdio 진입점에서는 표준출력이 MCP 메시지 통로이므로, 로그는 표준출력에 쓰지 않고 파일(또는 표준에러)에만 쓴다.

## 5. 데이터 모델

단일 사용자 시스템이므로 `user` 테이블은 두지 않는다. 마이그레이션은 drizzle-kit이 만든 SQL 파일로 관리한다.

### 5.1 Knowledge: 개념 그래프와 트랙

```
track          id, key UNIQUE, name, weight, description
concept        id, track_id, name UNIQUE, aliases text[], description,
               status (ACTIVE | PROPOSED | REJECTED),
               origin (SEED | INGESTION | CONVERSATION),
               auto_approved boolean, created_at, updated_at
concept_edge   from_id, to_id, type (PREREQUISITE | PART_OF | RELATED)
               PK (from_id, to_id, type), from_id <> to_id
```

- 간선 방향: `PART_OF`는 from이 to의 하위 개념, `PREREQUISITE`는 from을 알려면 to를 먼저 알아야 함. `RELATED`는 방향이 없어 id가 작은 쪽을 from으로 한 번만 저장한다.
- 선수 지식 체인과 근본 원인 탐색은 `WITH RECURSIVE` 쿼리로 조회한다. 학습 맥락에는 선수 개념을 2단계까지 싣는다.
- 시드(`src/core/knowledge/seed/<트랙>.yaml`)는 `npm run db:seed`로 반영한다(배포 스크립트도 돌린다). 트랙은 키로, 개념은 이름으로 찾아 트랙·별칭·설명을 시드대로 고치고, 승인 상태는 건드리지 않는다. 시드 개념끼리의 관계는 YAML대로 맞추며(빠진 관계는 지움), YAML에서 빠진 시드 개념(관계 포함)과 트랙은 지우고, 수집·대화에서 생긴 개념은 남긴다(ADR-0022). 학습 기록이나 경험 카드가 연결된 개념을 지우려 하면 적재 전체가 취소된다.
- 주제와 관련된 개념은 이름·별칭 매칭으로 고른다(`matchConcepts`). 주제 전체·단어와 같은 이름·별칭이 먼저이고, 주제 단어가 이름 안에 들어 있는 개념이 뒤다. 한글 단어 끝의 조사는 떼고도 비교하고, 2글자 영문 단어는 이름 안에서 찾지 않는다. 영문 별칭은 다른 영문 단어 안에서 걸리지 않게 단어 경계에서만 찾는다("nest"가 "nested" 안에서 걸리지 않게).

### 5.2 Memory: 원문, 청크, 경험 카드

```
source_document     id, source (NOTION), external_id, title, url,
                    summary, content_hash, source_updated_at, synced_at,
                    extraction_status (PENDING | DONE | FAILED), last_error
                    UNIQUE (source, external_id)
document_chunk      id, document_id, seq, chunk_hash, content
                    (최상위 제목 블록 단위 섹션, 7.1.
                     나중에 임베딩 컬럼을 추가할 단위)
experience          id, document_id NULL, origin (DOCUMENT | CONVERSATION),
                    project_name, title,
                    situation, task, action, result, lesson,   -- STAR+L 형식
                    occurred_at,
                    case_screen NULL (DECISION | NO_DECISION),  -- 판단 사례 선별 결과
                    created_at, updated_at
experience_concept  experience_id, concept_id
sync_cursor         source PK, last_synced_at
decision_case       id, experience_id UNIQUE,  -- 카드를 다시 뽑으면 함께 지워진다
                    situation, constraints text[],
                    options jsonb,             -- [{ text, chosen, reason }]
                    decision, rationale, outcome,
                    invariants text[],         -- 도메인을 바꿔도 남아야 하는 사실
                    kind (EXPERIENCE | HYPOTHETICAL),
                    status (PENDING | ACTIVE | REJECTED), review_note,
                    created_at, updated_at
decision_case_concept  case_id, concept_id
```

- `decision_case`(판단 사례)는 경험 카드에서 회사 맥락을 걷어낸 버전이다(ADR-0021). 회사 고유 이름이 들어 있지 않아야 하며, 상황 판단형 문제(7.3)의 재료가 된다. 카드 하나에 하나이고, 개념은 원래 카드의 개념을 그대로 잇는다(`decision_case_concept`). `review_note`는 게이트에 걸린 이유나 검토하며 남긴 말이다.
- `kind`는 사례의 종류다(ADR-0026). 경험 사례(`EXPERIENCE`)는 카드에 있는 사실만 쓰고, 가정 사례(`HYPOTHETICAL`)는 카드의 핵심 개념은 살리고 상황·조건을 새로 가정한다. 가정 사례는 "가정한 상황"이라고 밝혀 출제한다. 두 종류 모두 원래 카드의 개념을 이어 숙련도가 같은 개념에 쌓인다.

### 5.3 Mastery: FSRS와 숙련도

```
concept_mastery   concept_id PK,
                  -- FSRS 상태
                  stability, difficulty, state (NEW | LEARNING | REVIEW | RELEARNING),
                  reps, lapses, last_review_at, due_at,
                  -- 숙련도·약점 (힌트 없이 낸 응답만 반영)
                  mastery_score (0.0~1.0), weakness_score (0.0~1.0),
                  graded_attempts, updated_at
```

- 대화에서 다뤘거나(학습 기록의 DISCUSSED·CONFUSED) 풀이한 개념에만 행이 있다. 학습 기록이 연결한 개념은 NEW 상태로 기록 시각부터 복습할 수 있게 넣고, 이미 있으면 건드리지 않는다(ADR-0028).
- FSRS는 `ts-fsrs` 5.4.2(FSRS-6 기본 가중치)를 `fsrs.ts` 어댑터에서만 부른다(ADR-0016). 단기 학습 단계(1분·10분)는 꺼서 간격이 언제나 하루 이상이고, 상태는 NEW와 REVIEW만 생긴다(ADR-0028). 최대 간격은 36500일에서 180일로 줄였다(등급 사이 간격을 하루씩 벌려 실제로는 181~182일). 목표 기억률 0.9, 간격 흔들기 끔은 기본값 그대로다.
- 시드 적재로 개념을 지우려 하면 학습 기록처럼 외래 키가 막는다. 병합은 아래 규칙으로 옮긴다.

**개념 병합 (ADR-0028)**: `core`의 병합은 `tutor` 테이블을 모르므로, `core/knowledge`에 병합 참여 포트(`ConceptMergeParticipant`)를 두고 `tutor` 저장소가 구현해 모듈 시작 때 등록한다. `review_concept` 병합이 같은 트랜잭션에서 참여자를 부른다. 규칙: 학습 기록 연결은 대상 개념으로 옮기고 같은 기록에 둘 다 있으면 CONFUSED를 남긴다. 숙련도는 대상에 행이 없으면 원래 행을 옮기고, 둘 다 있으면 채점 수가 많은 쪽 행을 남긴다(FSRS 상태를 섞지 않는다). 퀴즈 문제·풀이는 `quiz`를 만들 때 같은 포트로 개념 ID만 바꾼다. 참여자를 등록하지 않은 진입점(수집 CLI)에서는 외래 키가 병합을 막는다.

### 5.4 Quiz: 문제와 풀이

```
quiz_question   id, concept_id,
                type (MULTIPLE_CHOICE | FILL_BLANK),
                angle (WHY | WHEN | TRADEOFF | MECHANISM | SCENARIO | MY_PROJECT),
                key_point,                 -- 이 문제가 확인하는 핵심 한 가지
                variant_of NULL,           -- 변형 문제면 원래 문제 ID
                difficulty (1~3), prompt,
                choices jsonb,             -- 객관식: [{ text, misconception NULL }]
                answer, accepted_answers text[],
                explanation, reference_material,
                experience_id NULL, case_id NULL,
                validation_status (PENDING | VALID | INVALID), validation_note,
                reported boolean, report_reason,
                used_count, created_at
quiz_attempt    id, question_id, user_answer, is_correct,
                confidence (SURE | UNSURE | GUESS),
                hint_used boolean, misconception,
                response_time_ms NULL, answered_at
```

- `validation_note`는 검증에 걸린 이유다(INVALID, ADR-0029). 객관식만 `choices`가 있고 `answer`는 정답 보기의 글이다. 보기는 4개다.
- 유형은 객관식·빈칸만 둔다(ADR-0019). 2026-10-18부터 복습에서는 객관식만 만들고 낸다(ENABLED_TYPES, ADR-0033). 빈칸은 시험에서 대부분 검증에 걸려 사용자가 다시 넣을지 정한다. 이미 있는 빈칸 문제는 남겨 두고 내지 않는다. 둘 다 코드가 즉시 채점하므로 채점 대기 상태가 없다. 서술형을 만들 때 유형, 채점 기준표, 점수·피드백, 채점 대기 상태를 함께 추가한다(12장).
- 객관식 오답 보기마다 그 보기가 나타내는 오개념을 붙인다. 오답을 고르면 그 오개념이 `quiz_attempt.misconception`에 남는다. 빈칸 오답은 사용자가 쓴 답(`user_answer`)을 그대로 남기고 다음 출제 때 참고한다.
- `key_point`와 `variant_of`로 "같은 핵심을 다른 상황에서 다시 묻는" 변형 문제를 원래 문제와 연결한다(7.3).
- `SCENARIO`는 판단 사례(`case_id`)로 만든 상황 판단형 객관식이다(ADR-0021). `MY_PROJECT`는 서술형 면접 연습용으로 남겨 두고, 서술형을 만들기 전에는 쓰지 않는다.

- 출제 지침(문제 품질에 대한 내 요청)은 `app_setting`(`quiz.guideline`)에 두고, 출제 프롬프트에 넣는다.
- `response_time_ms`는 응답 시간을 잴 수 있는 화면(MCP Apps, 원격 전환 때 검토)에서만 채운다. 텍스트 대화에서는 비워 둔다.

### 5.5 학습 기록, 예약 실행, 운영

```
study_note           id, topic, summary, confused_points text[],
                     answer_revealed boolean, created_at
                     (대화 중 Claude가 record_study_note 도구로 남긴다)
study_note_concept   note_id, concept_id, signal (DISCUSSED | CONFUSED)
                     PK (note_id, concept_id)
                     (record_study_note의 concepts를 이름·별칭으로 찾아 연결한다.
                      목록에 없는 이름은 연결하지 않고 결과로 알려 준다)
outreach_log         id, type (MORNING_REVIEW | DAILY_TOPIC | WEEKLY_REPORT),
                     run_date, requested_at, engaged_at, payload jsonb
                     UNIQUE (type, run_date)
scheduled_job        name PK, slot_date, status (RUNNING | SUCCEEDED | FAILED),

- `scheduled_job`은 서버 예약 작업마다 마지막 실행을 덮어쓴다. `slot_date`는 그 실행이 맡은 날짜(Asia/Seoul)이고 시작할 때 적는다(도중에 죽어도 그날 다시 돌지 않는다). `result`는 성공이면 단계별 요약, 실패면 오류다. 서버가 뜰 때 이것으로 놓친 실행을 찾는다(9장 "Mac 잠자기와 놓친 실행").

### 5.7 OAuth 인가 (원격 커넥터, ADR-0035)

흐름은 7.7. 토큰·코드·state·동의 값은 원문을 저장하지 않고 SHA-256 해시(hex)만 둔다. 시각은 `Clock`으로 넣고 만료는 코드에서 비교한다. 클라이언트는 CIMD라 클라이언트 테이블이 없다.

```
oauth_authorization_request  id, client_id, client_name, redirect_uri, code_challenge,
                             client_state, resource, google_state_hash UNIQUE,
                             google_nonce, google_code_verifier, email,
                             consent_token_hash UNIQUE, expires_at
                             (/authorize에서 만들고 구글 로그인·동의 동안 붙든다.
                              콜백에서 google_state_hash를 비우고 email·consent_token_hash를 채운다.
                              동의·거절하면 지운다. 수명 10분)
oauth_authorization_code     code_hash PK, client_id, redirect_uri, code_challenge,
                             resource, email, expires_at
                             (1회용, 토큰으로 바꾸면 지운다. 수명 5분)
oauth_grant                  id, client_id, email, resource, created_at, revoked_at
                             (로그인·동의 한 번에서 이어지는 토큰 계열)
oauth_access_token           token_hash PK, grant_id FK, expires_at   (수명 1시간)
oauth_refresh_token          token_hash PK, grant_id FK, expires_at, rotated_at
                             (수명 90일, 회전하면 rotated_at을 채우고 새 토큰을 다시 90일로)
```

- 만료된 인가 요청·코드는 `/authorize`가 올 때 지운다. 만료·폐기된 토큰 행은 지우지 않는다(한 사람이 쓰므로 쌓여도 작다).
- 액세스 토큰 검사는 해시로 찾고, 계열이 폐기되지 않았고, 만료 전이고, 계열의 `resource`가 이 서버의 MCP URL일 때만 통과한다.

## 6. 개념 어휘와 승인 정책

개념은 **통제 어휘**로 관리한다. 같은 개념이 여러 이름으로 흩어지지 않도록, Claude에게 항상 기존 개념 목록을 주고 "목록에서 먼저 고르고, 없을 때만 새 개념을 제안하라"고 지시한다.

| 단계 | 승인 방식 |
|---|---|
| 초기 시드 (커리큘럼: 트랙별 상위 개념과 강의 한 편 크기의 개념 + 관계) | 사용자가 정한 학습 목표로 Claude가 YAML(`src/core/knowledge/seed/<트랙>.yaml`)을 만들고 사용자가 검토한다(ADR-0022). 세부 개념은 수집 때 `PART_OF` 하위로 붙어 자동 승인된다 |
| 일회성 백필 | **조건부 자동 승인.** 기존 개념의 `PART_OF` 하위이면서 확신이 높으면 자동으로 `ACTIVE` 처리하고, 애매한 것은 승인 대기로 둔다. Claude 앱에서 "승인 대기 개념 보여줘"라고 하면 `list_pending_concepts`·`review_concept` 도구로 승인·거절·병합한다 |
| 정기 증분 동기화 | **자동 승인** + 안전장치 |
| 대화에서 나온 개념 | 증분 동기화와 같은 정책 |

### 자동 승인의 안전장치

1. **중복 검사 먼저:** 이름이나 별칭이 같거나 거의 같은 개념이 있으면, 새로 만들지 않고 기존 개념의 별칭으로 병합한다. "거의 같음"은 대소문자·공백·가운뎃점·하이픈을 무시하고 같은 것이다(`normalizeTerm`). 거절된 개념과 같은 제안은 되살리지 않는다.
2. **사후 확인:** 그 주에 자동으로 추가·병합된 개념을 주간 리포트에 표시한다. 되돌리거나 병합하려면 대화에서 `review_concept` 도구로 처리한다. 아무것도 하지 않으면 확정된다.

- **구현 상태 (2026-10-17):** `planConcepts`(`core/knowledge/concept-proposal.ts`)가 백필 정책(승인된 개념의 `PART_OF` 하위이고 Claude가 확신하면 자동 승인, 나머지는 승인 대기)을 적용한다. 지금 수집하는 문서는 모두 백필이라 증분 정책(모두 자동 승인)은 4단계 매일 동기화와 함께 더한다. 모르는 트랙을 제안하면 상위 개념의 트랙을 쓰고, 상위 개념도 없으면 버린다.

### 검토 도구

- `list_pending_concepts`: 승인 대기(`PROPOSED`) 개념과, 자동 승인됐지만 사람이 아직 보지 않은(`ACTIVE`이고 `auto_approved = true`) 개념을 카드가 많이 붙은 것부터 돌려준다. 개념마다 트랙, 상위 개념, 설명, 별칭, 카드 수, 앞쪽 카드 제목 3개를 싣는다.
- `review_concept`: 개념 하나를 이름이나 별칭으로 찾아 처리한다. 시드 개념은 YAML이 원천이라 바꾸지 않는다.
  - `APPROVE`: `ACTIVE`로 두고, 주면 이름·트랙·상위 개념·설명·별칭(전체 교체)을 고친다. `removeParent: true`를 주면 `PART_OF`를 지운다(`parent`와 함께 주면 거부한다. `parent: null`로 받으면 모델이 문자열 `"null"`을 보내 그 이름의 개념을 상위로 붙였다). 새 이름이 다른 개념의 이름·별칭과 겹치면 거부한다.
  - `MERGE`: 카드 연결과 하위 개념(`PART_OF`)을 대상 개념으로 옮기고, 이름과 별칭을 대상의 별칭으로 더한 뒤 개념을 지운다. 거절된 개념으로는 병합하지 않는다. 학습 기록 연결과 복습 일정도 대상 개념으로 옮긴다(5.3 "개념 병합").
  - `REJECT`: `REJECTED`로 둔다. 카드 연결은 남지만 조회·출제는 승인된 개념만 쓴다.
- `auto_approved`는 "자동 승인됐고 사람이 아직 보지 않았다"는 뜻이다. 검토하면(승인·거절) false가 되어 목록에서 빠진다.
- 승인·병합·거절은 사용자가 정한다. 서버 지침이 Claude에게 사용자가 답하지 않은 개념은 바꾸지 말라고 한다.

### 승인 대기 중 동작

- 경험 카드는 `PROPOSED` 상태의 개념에도 즉시 연결한다.
- `PROPOSED` 개념은 숙련도 추적, 출제, 학습 맥락(`get_learning_context`)에서 제외한다.
- 병합하면 연결이 기존 개념으로 옮겨진다.

### 7.0 `ClaudeCliClient` (백그라운드 작업)

```
claude -p --output-format stream-json --verbose --model <용도별 설정>
       --setting-sources "" --strict-mcp-config --no-session-persistence
       --tools "" (주제 탐색만 --tools "WebSearch,WebFetch" --allowedTools 같은 값)
       [--system-prompt <프롬프트>] [--json-schema <스키마>]
```

- 대화는 Claude 앱이 하므로, 이 클라이언트는 수집·추출, 출제·검증, 요약 같은 대화 밖 작업에만 쓴다(서술형을 만들면 서술형 채점도).
- 프롬프트는 표준입력으로 전달한다. 출력은 줄마다 JSON 이벤트 하나이며, 끝까지 읽은 뒤 `result` 이벤트와 마지막 `rate_limit_event`만 해석한다 (ADR-0012).
- 성공 여부는 `is_error`로 판단한다(`subtype`은 오류여도 `"success"`일 수 있다). 미로그인은 `result` 문자열(`Not logged in`)로, 한도 초과는 `rate_limit_event`의 상태와 `resetsAt`으로 판별한다.
- 구조화된 출력은 `--json-schema`로 받아 `structured_output`을 zod 스키마로 다시 검증한다. `--json-schema`에 넘기는 JSON Schema도 같은 zod 스키마에서 만든다.
- 빈 전용 작업 디렉터리에서 실행한다. 이 디렉터리와 상위 디렉터리에 CLAUDE.md가 없어야 한다. `--setting-sources ""`가 CLAUDE.md 로드를 막는 것은 스파이크로 확인했다.
- 실행 파일 경로는 설정값으로 받는다 (OS마다 다를 수 있다). `--bare`는 구독 로그인을 읽지 않아 쓰지 않는다.
- 도구는 기본적으로 끈다. 주제 탐색과 문제 출제(`QUIZ_GENERATION`, ADR-0033)에만 `WebSearch`, `WebFetch`를 허용한다. 출제는 제품·엔진·버전에 따라 갈리는 사실을 확인할 때만 검색하고, 확인한 문서 주소를 기준 자료에 적는다.
- 동시 실행은 최대 5개(세마포어, ADR-0027). 판단 사례 추상화는 카드를 그 수만큼 함께 처리한다. 용도별 타임아웃을 두고, 타임아웃이 나면 1회 재시도한다.
- JSON 형식이 깨지면 오류 내용을 붙여 1회 재요청한다.
- 모든 호출을 `llm_call_log`에 기록한다.
- 용도별 모델은 `claude.settings.ts`에서 지정한다. 2026-10-17 결정: 경험 카드 추출과 판단 사례 선별·치환은 Sonnet, 판단 사례의 독립 검증은 Opus(사용량과 품질의 절충). 2026-10-18 결정(ADR-0026): 가정 사례 생성은 Sonnet(`CASE_HYPOTHETICAL`), 정답을 숨긴 풀이 검증은 Opus(`CASE_HYPOTHETICAL_VERIFICATION`). 출제는 Sonnet(웹 검색 허용, ADR-0033), 출제 검증은 Opus(웹 없이 정답을 모른 채 풂, ADR-0029). 채점은 코드가 한다.

### 7.1 수집 (백필, 증분 동기화)

```
트리거: 최초 백필, npm run sync, 매일 04:00 새벽 작업(동기화 → 추출 → 추상화, 7.4), sync_now(동기화 → 추출)

1. 수집 범위 안 문서 목록을 받는다. Notion 검색 API로 공유된 항목을 모두 받고, 상위를 따라가 루트 아래 페이지만 고른다
   (블록 안에 놓인 페이지는 블록의 상위를 따라 올라간다). 저장된 원천 수정 시각과 같은 문서는 본문을 읽지 않는다
2. 바뀐 문서의 블록을 하위까지 읽어 청크로 나눈다 → 청크 해시를 비교해 추가·수정·삭제된 청크를 찾는다
   (본문이 같으면 메타데이터만 고친다. 목록에 없는 문서는 청크와 함께 지운다. 목록이 비면 지우지 않고 멈춘다)
3. 바뀐 청크가 없으면 건너뛴다. 본문이 바뀐 문서는 추출 상태를 PENDING으로 돌린다

추출 (npm run extract, 지금은 동기화와 따로 돌린다)
4. PENDING·FAILED 문서마다 Claude 추출 호출 (Sonnet, 구조화 출력)
   - 입력: 트랙 키 + 개념 목록(이름·트랙·별칭, 거절된 개념은 뺌) + 문서 본문 전체(최대 2만 자 정도라 한 번에 넣는다)
   - 출력: 경험 카드(STAR+L, 카드마다 개념 이름), 새 개념 제안(트랙, 상위 개념, 확신 여부), 문서 요약
5. 판단이 들어 있는 경험 카드에서 판단 사례를 추상화한다 (아래 "판단 사례". 지금은 추출과 따로 `npm run abstract`로 돌린다)
6. 승인 정책(6장)을 코드로 적용하고 하나의 트랜잭션으로 반영한다. 그 문서에서 뽑았던 카드는 지우고 새 카드로 바꾼다
7. 실패한 문서는 FAILED로 표시하고, 다음 실행 때 재시도한다 (다른 문서 처리는 계속). 사용량 한도·로그인 오류면 남은 문서를 그대로 두고 멈춘다
```

- **다시 뽑을 때 카드를 통째로 바꾼다.** 지금은 카드를 참조하는 곳(문제, 학습 기록)이 없어 카드 id가 바뀌어도 된다. 카드를 참조하는 기능이 생기면(3단계) 기존 카드를 입력에 넣고 추가·수정안을 받는 방식으로 바꾼다.
- 카드의 개념 이름은 이름·별칭이 정규화 기준으로 같은 개념에 잇는다(`resolveConcept`). 목록에도 새 개념 제안에도 없는 이름은 버린다.

- 동기화는 매일 04:00 새벽 작업이 하고(7.4), 손으로는 `npm run sync`(진입점 `sync.ts`)로 돌린다. 새벽 작업과 `sync_now`는 같은 수집 파이프라인(`IngestionPipeline`: 동기화 → 추출(→ 추상화))을 쓰고, 앞 단계가 실패해도 뒤 단계는 한다(추출은 PENDING·FAILED 문서, 추상화는 선별하지 않은 카드가 대상이라 지난번 남은 것도 처리한다). 추출·추상화가 사용량 한도나 로그인 문제로 멈추면 그 단계를 실패로 둔다.
- **`sync_now`:** 대화에서 동기화 → 추출을 뒤에서 시작하고 바로 "시작했다"를 돌려준다. 진행·결과는 `sync_status`(지금 도는지, 마지막 동기화 시각, 문서·청크 수, 추출 상태별 문서 수)로 본다. 새벽 작업과 같은 DB advisory 잠금(`ingestion`)을 써서 이미 돌고 있으면 시작하지 않고 그렇다고 답한다. 추출이 구독 사용량을 쓴다고 도구 설명에 적었다. 판단 사례 추상화는 하지 않는다(새벽 작업이 한다). stdio 서버에서 부르면 Desktop이 프로세스를 끌 때 작업이 끊기고, 다음 실행이 이어서 한다.
- **청크:** 최상위 제목 블록(heading 1~3)마다 새 청크를 시작한다. 블록 하나씩 나누면 목록 한 줄이 청크 하나가 되어 바뀐 청크만 넘길 때 맥락이 끊긴다. 하위 블록은 들여쓴 줄로 붙이고, 제목·목록·할 일·인용·코드는 마크다운 기호로 남긴다. DB 행의 분류 속성(예: 섹션)은 첫 청크로 넣는다. 하위 페이지는 따로 수집하는 문서라 본문을 따라 들어가지 않는다.

**판단 사례** (ADR-0021, ADR-0026)

업무 문서의 경험은 회사 테이블·데이터 원천·업무 규칙 위에서 쓰였다. 그대로 문제로 만들면 회사 사정을 알아야 풀 수 있고, 회사 고유 정보가 문제와 대화에 퍼진다. 그래서 수집할 때 한 번 추상화해 `decision_case`로 저장하고, 출제는 이것으로 한다.

0. **선별 (`claude -p`, Sonnet, 카드 40장씩 한 번에):** 상황 판단형 문제로 만들 만큼 판단이 분명한 카드만 고른다(사용자 결정 2026-10-18). 둘 이상의 선택지와 고른·버린 이유가 카드에 적혀 있고(되돌린 판단 포함) 그 이유가 일반 원칙이어야 한다. 선택지 없는 작업 기록, 다른 방법을 따지지 않은 버그 수정·진단, 교훈이 여러 방법을 모두 맞다고 하는 카드, 정리 노트, 회사 규칙만이 근거인 카드는 뺀다. 애매하면 뺀다. 결과는 `experience.case_screen`에 남겨 다시 묻지 않는다.
1. **추출 (`claude -p`, 구조화 출력):** 상황, 제약, 선택지(고른 것과 고르지 않은 이유), 결정, 근거, 결과, 불변 조건, 연결 개념을 받는다. 특정 조직을 가리키는 이름(회사·고객사·협력사, 사내 시스템·DB·테이블·컬럼·코드값, 서버 주소)은 지우지 않고 역할 설명으로 치환해 일반 상황으로 고쳐 쓴다. 회사 용어 목록은 쓰지 않는다(ADR-0024). 불변 조건은 도메인을 바꿔도 반드시 남아야 하는 사실이다(예: "원천 테이블은 기존 행을 제자리에서 UPDATE한다").
2. **패턴 게이트 (코드):** 결과 전체를 정규식으로 검사하고 통과·거부만 한다. 검사 대상은 목록 없이 모양으로 잡히는 IP 주소, URL·도메인, `UPPER_SNAKE` 식별자다. 보기 모양으로 정답이 드러나는지도 본다: 정답 보기가 가장 긴 오답의 1.5배를 넘으면 걸린다(2026-10-18 시험에서 7장 모두 정답이 가장 길었다. 처음 1.3배는 경험 사례를 자주 걸어 늦췄다). 걸리면 걸린 문자열이나 길이를 붙여 1회 다시 추출한다.
3. **독립 검증 (`claude -p`, Opus, 별도 호출):** 원문과 추상화본을 함께 주고 묻는다. 같은 근거로 같은 결론이 나오는가, 불변 조건이 모두 살아 있는가, 회사 밖 사람이 이 사례만 보고 이해할 수 있는가(특정 조직을 가리키는 이름이 남았는가).
4. 통과하면 경험 사례(`EXPERIENCE`)로 `ACTIVE`가 된다. 두 번 다 걸리면 가정 사례로 폴백한다(ADR-0026).
5. **가정 사례 (`claude -p`, Sonnet):** 경험 카드와 경험 사례가 걸린 이유를 주고, 카드의 핵심 개념·키워드는 살린 채 상황·조건을 새로 가정한 판단 사례를 받는다(응답 모양은 경험 사례와 같다). 정답의 근거는 일반 원칙이고, 버린 선택지마다 틀리게 되는 조건을 제약에 둔다. "내가 했다"는 쓰지 않는다. 패턴 게이트를 똑같이 거친다.
6. **풀이 검증 (`claude -p`, Opus, 정답을 숨김):** 상황·제약·선택지 문장만 번호를 붙여 보내고(고른 표시·이유·결정·근거는 뺀다) 직접 풀게 한다. 고른 번호가 사례의 정답과 같고, 정답이 하나로 정해지고, 회사 밖 사람이 이해할 수 있고, 남은 이름이 없으면 통과다. 걸리면 이유(다른 번호를 골랐으면 그 사실)를 붙여 1회 다시 만든다. 통과하면 `HYPOTHETICAL`로 `ACTIVE`가 된다.
7. 가정 사례도 두 번 다 걸리면 마지막 경험 사례를 `PENDING`으로 두고(`review_note`에 "경험 사례:"와 "가정 사례:" 아래로 두 쪽의 걸린 이유) Claude 앱 대화에서 `list_pending_cases`·`review_case`로 승인·수정·거절한다(개념 승인 정책과 같은 구조). 자동 승인된 사례는 주간 리포트에서 사후 확인한다(4단계).

- 실무 결정이 일반적인 정답은 아닐 수 있다. 결정을 되돌린 기록이 있으면 되돌린 뒤의 판단과 그 이유를 근거로 쓴다.
- **구현 상태 (2026-10-18):** 가정 사례 폴백(5~7)을 만들었다. `npm run abstract` 출력은 경험·가정·PENDING 수를 따로 센다. 경험 사례 프롬프트는 "고르거나 버린 이유가 카드에 없는 선택지는 뺀다(남는 선택지가 둘 미만이면 그대로 쓰고 검증에 맡긴다)"로 바꿨다. 그 전에 선별·치환·패턴 게이트·독립 검증과 진입점(`npm run abstract`, `--limit`·`--ids`)까지 만들었다. 원문은 경험 카드(STAR+L)만 넣고 문서 본문은 넣지 않는다. 게이트나 검증에 걸리면 걸린 문자열·문제를 붙여 한 번 다시 쓰고(카드당 치환 최대 2회, 검증 최대 2회), 그래도 걸리면 마지막 결과를 `PENDING`으로 저장한다. 검토 도구도 만들었다. `list_pending_cases`는 PENDING 사례를 걸린 이유, 본문, 원래 카드와 함께 오래된 것부터 보여 주고(기본 5개), `review_case`는 승인(주는 본문 필드만 통째로 바꿈)·거절(`note`에 이유)을 반영한다. 고쳐서 승인할 때도 패턴 게이트를 다시 거쳐, 걸리면 바꾸지 않는다. 응답 스키마의 선택지(`options`)에 "고른 이유·버린 이유"를 묻는 설명을 달면 Sonnet의 안전 장치(`reasoning_extraction`)에 걸려 응답을 받지 못했다(첫 시험 10장 중 9장). 그래서 선택지 규칙은 스키마 설명이 아니라 시스템 프롬프트에 둔다.
- **10장 시험 (2026-10-18):** 치환 프롬프트에 "카드에 있는 사실만 쓰기"와 "문제로 쓸 수 있게 쓰기"(진단 결과·정답을 상황·제약에 넣지 않기, 버린 선택지가 틀리게 되는 조건을 제약에 쓰기, 맥락 풀어 쓰기)를 더하자 같은 10장의 ACTIVE가 2장에서 5장이 됐다. 남은 PENDING은 사실 지어내기 3, 정답이 여럿 2, 소문자 컬럼 이름 누출 1(패턴 게이트로는 못 잡고 검증이 잡음)이다. 선별 기준을 좁히자 처음 40장 중 고른 카드가 33장에서 19장이 됐다. 같은 카드라도 실행마다 결과가 달라질 수 있다.

### 7.2 튜터링 대화

```
시작: Claude Desktop에서 새 대화를 열고 질문한다 (MCP 서버가 켜져 있으면 도구를 쓸 수 있다)
     튜터 지침을 넣은 Claude 프로젝트 안에서 대화하면 지침이 항상 적용된다
     저녁 주제·퀴즈 결과 대화에서 이어서 물어봐도 같은 흐름이다

대화 중:
 1. Claude가 get_learning_context(topic)를 부른다
    → 관련 개념(별칭 매칭)과 상위·선수 개념, 관련 개념에 연결된 경험 카드(최대 3장, 제목·교훈·상황·원문 링크),
      주제 글자나 관련 개념으로 찾은 지난 학습 기록, 최근 학습 기록
      (그 개념의 숙련도·약한 선수 개념은 3단계에서 더한다)
 2. Claude가 교수 규칙(7.5)에 따라 대화한다. 경험 카드가 있으면 "네가 겪은 ○○과 같은 원리"로 짧게 연결한다.
    사용자가 자기 경험을 찾거나 카드를 자세히 봐야 하면 search_experience(query)로 STAR+L 전체를 가져온다.
    웹 검색은 Claude 앱 기능을 쓴다
 3. 대화가 마무리되거나 헷갈린 지점이 분명해지면 Claude가 record_study_note를 부른다
    → 주제, 요약, 헷갈린 점, 답 공개 여부, 관련 개념(DISCUSSED | CONFUSED)
    → 대화에서 새 경험이 드러나면 경험 카드 후보로 저장한다 (자동 승인 정책)
```

- 경험 카드 찾기: 학습 맥락은 승인된 개념에 연결된 카드만 싣는다(맞은 개념이 많은 것부터, 같으면 최근 경험부터). `search_experience`는 개념으로 찾은 카드 뒤에 제목·STAR+L 글자 검색 결과를 붙인다. 그래서 거절된 개념(트랙 밖 분야)에만 연결된 카드도 글자로는 찾는다. 임베딩은 쓰지 않는다(ADR-0005).
- 세션, 메시지 저장, 유휴 종료, 대화 요약은 서버에 두지 않는다. Claude 앱의 대화가 그 역할을 한다.
- `record_study_note`는 Claude가 불러야만 남는다. MCP 서버의 `instructions`와 도구 설명, Claude 프로젝트 지침으로 부르도록 유도하고, 반드시 남는다고 가정하지 않는다.
- 대화 결과로는 숙련도 점수를 바꾸지 않는다. `CONFUSED` 신호는 출제 우선순위만 올린다. 숙련도는 퀴즈 결과로만 갱신한다. 다만 기록이 연결한 개념은 복습 일정이 없으면 새로 넣어, 다음 복습에서 확인한다(ADR-0028).

### 7.3 퀴즈와 복습

```
시작: Claude Desktop 대화에서 "복습하자", "OO 문제 내줘" (get_review_set)
     아침 복습 예약 작업은 5단계에서 붙인다 (ADR-0019·0034)

1. 개념 선택 우선순위 (근본 원인 후보가 맨 앞, 8장)
   ① 오늘(Asia/Seoul) 안에 due_at이 오는 개념 (저녁 주제를 붙이는 6단계 뒤: 전날 저녁 주제 개념은 반드시 포함)
   ② 약점 개념, CONFUSED 신호가 있는 개념
   ③ 트랙 가중치에 따른 새 개념
   하루 최대 10문제. 넘치면 우선순위가 높은 것만 낸다
2. 개념마다 낼 문제를 고른다 (아래 "변형 문제")
   ① 그 개념에서 틀렸거나 불안하게 맞힌 문제가 있으면 그 문제의 변형
   ② 없으면 이미 확인한 핵심의 변형과 아직 묻지 않은 핵심을 번갈아
   풀에 VALID인 문제가 없으면 뒤에서 생성 + 검증하고 결과에 "만드는 중"으로 알린다(ADR-0030). 뒤에서 만든 문제가 하나도 검증을 통과하지 못하면 그 개념은 30분 동안 다시 만들지 않고 "만들지 못함"으로 알린다(부를 때마다 다시 만들면 사용량만 쓴다. 서버 메모리에만 두어 다시 띄우면 풀린다). 한 번 푼 문제는 그대로 다시 내지 않는다
3. get_review_set은 문제 ID, 유형, 질문, 보기만 돌려준다 (정답·해설·기준 자료 없음)
4. Claude가 한 문제씩 묻고, 답을 들은 뒤 확신도(확실·애매·찍음)를 묻는다
5. Claude가 submit_answer(questionId, answer, confidence, hintUsed)를 부른다 → 서버가 즉시 채점
   - 객관식: 정답과 비교. 오답이면 고른 보기의 오개념을 기록
   - 빈칸: answer와 accepted_answers로 비교 (공백·대소문자·전각/반각 정규화). "팬아웃(fan-out)"처럼 두 표기를 괄호로 함께 쓰면 괄호 앞이나 안 중 하나만 맞아도 정답
6. 결과(정오, 해설, 기록된 오개념, 관련 경험 카드)를 돌려주고 Claude가 설명을 이어간다
7. 갱신: FSRS 상태, 숙련도·약점 점수 (8장 규칙)
```

- 텍스트로 묻고 답한다. 객관식 버튼, 확신도 버튼, 응답 시간 측정은 원격 전환 때 MCP Apps로 검토한다.
- 확신도와 힌트 사용 여부는 Claude가 대화에서 받아 넘긴다. 빠지면 `UNSURE`, 힌트 사용으로 보수적으로 처리한다.
- 채점은 LLM을 부르지 않으므로 사용량 한도와 상관없이 미리 만든 문제로 복습을 이어 간다.
- 문제를 만드는 데 1~2분 걸려 `get_review_set`이 기다리지 않는다(ADR-0030). 풀이 비어 있으면 첫 호출은 "만드는 중"만 돌려주고, 다시 부르면 나온다. 문제 풀 보충(7.4)이 생기기 전까지는 `npm run quiz`로 미리 채울 수 있다.
- 우선순위 ①은 "지금 시각까지"가 아니라 "오늘(`Clock.timeZone`, Asia/Seoul) 날짜가 끝나기 전"에 예정일이 오는 개념이다(2026-10-20 사용자 결정). 아침 알림의 "오늘 복습 N개", 새벽 문제 보충, `get_review_set`이 같은 "오늘 복습할 개념"을 쓰게 해서(`QuizReviewService`의 한 곳) 아침에 받은 개수와 실제로 받는 문제가 어긋나지 않게 한다. 예정일보다 몇 시간 일찍 푸는 셈이지만 FSRS 일정 계산(ts-fsrs)은 그대로이고, 실제로 푼 시각으로 다음 일정을 잡는다. ADR-0030의 "복습할 때가 된 개념"을 이 뜻으로 읽는다.
- 우선순위 ②의 CONFUSED는 헷갈렸다고 기록한 뒤 아직 퀴즈로 확인하지 않은 개념이다. ③ 새 개념은 트랙 가중치에 비례해 뽑는다. 하루 10문제는 그날 채점한 풀이 수로 세고, 개념을 골라 달라고 했을 때(기본 3문제)는 세지 않는다(ADR-0030).
- 객관식 답은 보기 번호로 받는다. 같은 오개념이 그 개념에서 전에도 나왔으면 반복 오개념이다(8장).

**문제 생성 규칙**

- 출제 각도는 "왜 / 언제 쓰나 / 트레이드오프 / 동작 원리 / 이 상황에서는(상황 판단)"을 우선한다. "용어 ↔ 정의" 형태는 피한다.
- 같은 개념을 복습할 때마다 다른 문제(바꿔 묻기)를 낸다.
- 문제마다 확인할 핵심(`key_point`)을 하나만 둔다. 핵심이 둘이면 문제를 나눈다.
- 출제할 때 기준 자료(정답 근거, 해설, 출처: 경험 카드나 웹 자료)를 함께 넣고, `reference_material`에 저장한다.
- **약점을 문제 내용에 반영한다.** 출제 프롬프트에 그 개념의 최근 오개념(`quiz_attempt.misconception`), 빈칸 오답, 학습 기록의 헷갈린 점(`study_note.confused_points`), 경험 카드에 적힌 내 실수를 넣는다. 오답 보기와 빈칸 자리는 이 지점을 겨냥한다. 근거가 없으면 흔한 오개념으로 만든다.
- 빈칸은 답이 거의 하나로 정해지는 용어·값 자리에 둔다. 표기가 갈리는 답(약어, 영문·한글)은 `accepted_answers`에 모두 넣는다.
- 출제 지침(`quiz.guideline`)을 프롬프트에 넣는다. "이런 문제는 내지 마" 같은 요청은 대화에서 `update_quiz_guideline` 도구로 고친다(재배포 없이 품질 조정).

**변형 문제** (망각 방지)

- 복습 시기는 FSRS가 개념 단위로 정한다(ADR-0016). 그 개념을 다시 낼 때 이미 풀었던 문제를 그대로 내지 않고, 같은 `key_point`를 다른 상황으로 묻는 변형을 낸다(`variant_of`에 원래 문제).
- 틀렸거나, 찍어서 맞혔거나, 힌트를 쓴 문제는 다음 복습 때 변형을 우선 낸다. 확실하게 맞힌 핵심도 간격을 두고 변형으로 다시 확인한다.
- 문장만 바꾸면 이해가 아니라 "그 문제 답은 B였지"라는 기억으로 풀게 된다. 핵심은 그대로 두고 상황·조건·각도(왜 → 언제 쓰나 → 이 조건에서도 맞나)를 바꾸고, 유형(객관식 ↔ 빈칸)도 바꿀 수 있다.
- 변형 문제 생성 프롬프트에는 원래 문제, 그때의 답과 오개념을 넣는다.
- 구현: 문제의 마지막 풀이가 틀림·찍음·힌트면 흔들린 문제, 힌트 없이 찍지 않고 맞혔으면 확인된 문제다. 개념에 새 문제를 만들 때 ① 변형이 없는 흔들린 문제의 변형 ② 없으면 가장 최근 문제가 변형이 아니고 변형이 없는 확인된 문제가 있을 때 그 변형, 아니면 새 핵심(번갈아). 변형은 원래 문제의 `key_point`를 그대로 쓰고 `variant_of`로 잇는다. 낼 때는 변형을 먼저 낸다.
- 변형 검증: 질문·보기·정답 보기가 원래와 같으면 코드가 거르고, 정답을 숨긴 풀이 뒤에 원래 문제와 변형을 함께 주는 비교 호출(Opus)이 같은 핵심인지, 원래 답을 외워서 풀 수 있는지 본다. 걸리면 1회 다시 쓰고, 그래도 걸리면 `INVALID`(다음에 다시 만든다).
- `npm run quiz -- --variant-of <문제 번호>`로 변형을 만들어 볼 수 있다.

**검증 단계와 피드백**

- 흐름(ADR-0029): 출제(Sonnet) → 모양 검사(코드: 보기 4개·정답 보기 하나·오답마다 오개념·정답만 긴 보기, 빈칸 `____` 하나·정답 노출, 패턴 게이트) → 보기 섞기(코드) → 정답을 숨긴 풀이 검증(Opus). 걸리면 이유를 붙여 1회 다시 쓰고, 그래도 걸리면 `INVALID`로 남긴다. 약점 재료는 지금 학습 기록의 헷갈린 점과 경험 카드이고, 오답 오개념·빈칸 오답은 `quiz_attempt`와 함께 더한다.
- 출제 지침은 한 줄에 규칙 하나로 `app_setting`(`quiz.guideline`)에 둔다. `update_quiz_guideline(add, remove)`로 고치고, 인자 없이 부르면 지금 지침을 돌려준다.
- 품질 확인은 `npm run quiz -- --concept <이름>`으로 문제를 만들어 본다.

- 문제를 생성한 직후 별도 Claude 호출로 확인한다: 정답이 하나뿐인지, 정답이 보기 안에 있는지(객관식), 허용 답이 맞는 표기를 모두 담는지(빈칸), 기준 자료만으로 풀 수 있는지. 변형 문제는 원래 문제와 핵심이 같은지, 원래 문제의 답을 외워서는 풀 수 없을 만큼 다른지도 확인한다.
- 통과한 문제만 `VALID`가 된다.
- 대화에서 "이 문제 이상해"라고 하면 Claude가 `report_question(questionId, reason)`을 부른다. `reported = true`로 표시하고 출제에서 뺀다. 그 풀이는 숙련도 계산에서 제외한다. 이미 반영한 풀이도 빼야 하므로, 그 개념의 숙련도·약점과 FSRS 일정을 신고된 문제를 뺀 풀이 기록으로 처음부터 다시 계산한다(8장). 신고 이유는 출제 지침을 고칠 때 참고한다.

**상황 판단형 문제** (`angle = SCENARIO`, `case_id` 있음, ADR-0021)

- 판단 사례로 만든 객관식이다. 가상의 상황과 조건을 주고 판단을 묻는다. 회사 이름·테이블·업무 규칙 없이 문제만 읽고 풀 수 있어야 한다.
- 질문 틀을 좁게 잡는다. 예: "가장 먼저 확인할 것은?", "이 선택의 가장 큰 위험은?", "이 조건에서 가장 적절한 순서는?"
- 정답의 근거는 일반 원칙이다. 정답이 하나로 정해지도록 상황에 조건을 명시한다(예: "다운타임 불가", "배포 중 구버전 앱이 함께 떠 있음").
- 오답 보기는 판단 사례의 고르지 않은 선택지와, 원문에 남은 내 실제 실수로 만든다.
- 변형 문제는 같은 판단 사례를 다른 도메인으로 바꿔 낸다(주문·상품, 예약·좌석 등). 불변 조건은 그대로 둔다.
- 생성한 문제도 패턴 게이트를 다시 통과해야 한다. 검증 단계에서는 정답을 주지 않은 별도 호출이 문제만 보고 푼다. 정답을 맞히지 못하거나 모르는 용어·정보 부족을 말하면 `INVALID`다.
- 경험 카드와 원문은 문제에 싣지 않는다(출제 프롬프트에도 판단 사례만 넣는다). `submit_answer` 결과에 경험 사례면 "이 원칙을 실제로 겪은 경험", 가정 사례면 "같은 개념을 다룬 내 경험"으로 사례를 뽑은 경험 카드 제목을 보여 준다(ADR-0032).
- 출제 순서(ADR-0032): 흔들린 문제의 변형 → 아직 문제로 만들어 보지 않은 ACTIVE 사례가 있고 상황 판단형 차례면(아직 상황 판단형이 없거나, 마지막 상황 판단형 뒤로 개념 문제가 두 개 나왔으면. 개념 2 : 상황 판단형 1, ADR-0033) 상황 판단형 → 개념 문제(확인된 핵심의 변형과 새 핵심을 번갈아). 한 번 문제로 만들어 본 사례는 검증 결과와 상관없이 다시 고르지 않고, 통과한 문제는 변형으로 다른 도메인에서 다시 묻는다.
- 가정 사례로 만든 문제는 질문 앞에 `[가정한 상황] `을 코드가 붙인다(ADR-0026·0032).

**내 프로젝트 문제** (`angle = MY_PROJECT`)

- 객관식으로 내지 않는다. "이 프로젝트에서 X 대신 Y를 고른 이유는?"은 회사 사정을 기억해야 풀 수 있어 `SCENARIO`로 대신한다(ADR-0021).
- 경험을 먼저 말로 설명하게 하고 카드 내용(STAR+L)과 비교하는 면접형 서술 연습에 남겨 두고, 서술형과 함께 만든다(ADR-0019, 12장). 그동안은 튜터링 대화에서 연습한다.

### 7.4 먼저 말 걸기

**아침 복습은 5단계, 나머지는 6단계로 미룬다 (ADR-0019·0034).** 그 전까지는 대화에서 "복습하자"처럼 직접 시작한다. 5단계 실행 방식은 ADR-0036으로 정했다(아래 "5단계 구현"). 저녁 주제·주간 리포트의 시각은 목표다.

서버는 Claude 앱에 먼저 말을 걸 수 없다. 정해진 시각에 Claude 쪽 예약 작업이 도구를 불러 대화를 만들어야 한다.

- 확인한 것(2026-10-14): Cowork 예약 작업은 로컬 MCP 서버를 쓸 수 없다. Claude Code 클라우드 루틴은 Anthropic 클라우드에서 돌아 로컬 MCP에 닿지 않는다.
- 남은 후보: Claude Code 데스크톱 예약 작업(이 레포의 MCP 설정 사용, 맥미니가 깨어 있고 앱이 켜져 있어야 함), 원격 전환(4단계) 뒤의 예약 작업·클라우드 루틴.
- 정할 때 확인할 것: 예약 작업이 MCP 도구를 부르는지, 실행 결과를 휴대폰 Claude 앱에서 볼 수 있는지, 그 대화를 이어갈 때 도구를 쓸 수 있는지.

| 시각 | 내용 | 실행 주체 |
|---|---|---|
| 매일 04:00 | **새벽 준비:** 증분 동기화 → 경험 카드 추출 → 판단 사례 추상화 → 오늘 복습할 개념 중 낼 문제가 없는 개념의 문제 미리 만들기(하룻밤 최대 10개 개념) | MCP HTTP 서버의 스케줄러, `claude -p` |
| 매일 **07:30** | **아침 복습:** `get_review_set`으로 복습할 개념의 문제를 최대 10개까지 낸다(6단계 뒤: 전날 저녁 주제를 반드시 포함). 서버는 설정으로 켜는 ntfy 아침 알림 "오늘 복습 N개"를 보낸다 | Cowork 예약 작업(원격 커넥터, 시험 중) 또는 ntfy 알림 뒤 사용자가 "복습하자" |
| 평일 21:00 | **저녁 알림:** 그날 푼 문제가 없고 오늘 복습할 개념이 있으면 ntfy로 알린다. 토요일·일요일(Asia/Seoul)에는 보내지 않는다 | MCP HTTP 서버의 스케줄러 |
| 매일 18:30 | **오늘의 주제:** `get_daily_topic`이 근본 원인 후보, 약점, 다음 학습 개념 순으로 하나를 고르고 관련 경험을 돌려준다. Claude가 생각해볼 질문을 만든다 | Claude 예약 작업 |
| 일요일 20:00 | **주간 리포트:** `get_weekly_report`가 학습량, 정답률 변화, 좋아진 개념·약한 개념, 반복 오개념, 트랙별 비중, 경험 카드 설명 연습 현황, 자동 승인 개념 목록, 수집 실패를 돌려주고, Claude가 정리하고 다음 주를 추천한다 | Claude 예약 작업 |

- 복습할 개념이 없는 날은 `get_review_set`이 "오늘은 복습 없음"을 돌려준다.
- 반응했는지(`engaged_at`)는 그 날의 도구가 실제로 쓰였는지(답안 제출, 주제 대화 기록)로 판단한다. 같은 유형을 3번 연속 무시하면 주간 리포트에서 알리고 시각·빈도 조정을 권한다. 예약 작업의 일정은 Claude 앱에서 바꾼다.

**5단계 구현 (ADR-0036, 2026-10-20):**

- **스케줄러 (`core/scheduler`):** 상시 실행 MCP HTTP 서버 안에서 `@nestjs/schedule`로 돈다(같은 이벤트 루프). 작업은 `@ScheduledJob()`을 붙인 `DailyJob`(이름, `HH:MM`, 잠금)이고, 시각은 `Asia/Seoul`이다. stdio 서버·CLI·테스트 앱에는 스케줄러를 넣지 않는다.
- **실행 규칙:** 작업은 DB advisory 잠금을 잡고(같은 작업이나 같은 잠금을 쓰는 일이 돌고 있으면 건너뜀, 프로세스가 달라도 막힘), `scheduled_job`의 `slot_date`가 오늘이면 돌지 않는다. 크론 시각과 서버 시작이 모두 이 규칙으로 부르므로 하루에 한 번만 돈다. 실패는 운영 알림(`SCHEDULED_JOB_FAILED`)으로 보낸다.
- **서버 시작:** DB를 5초 간격으로 12번까지 기다린 뒤(닿지 않으면 프로세스를 끝내 launchd `KeepAlive`가 다시 띄움), 작업마다 오늘 시각이 지났고 오늘 몫을 돌리지 않았으면 한 번 따라잡는다. 어제 이전 몫은 따라잡지 않는다.
- **오늘 복습할 개념:** 복습 세트의 우선순위(근본 원인 → 오늘(Asia/Seoul) 안에 예정일이 오는 개념 → 헷갈렸다고 기록한 개념 → 약점)대로 오늘 남은 수(하루 상한 10 − 오늘 푼 수)까지다. `get_review_set`도 같은 정의로 고르고, 모자라면 새 개념으로 채운다. 새 개념은 복습 세트가 그때그때 무작위로 뽑으므로 알림 개수와 새벽 보충에는 넣지 않는다. 새벽 작업은 이 중 낼 문제(검증 통과·신고 안 됨·아직 안 푼 문제)가 없는 개념마다 한 문제씩 만든다.
- **학습 알림 (`tutor/outreach`, `StudyNotifier`):** 운영 알림과 같은 ntfy 토픽이고 종류를 나눈다(우선순위 보통, 책 태그, 1시간 묶기 없음). 본문에는 개수와 시작하는 법(Claude 앱에서 "복습하자"라고 말한다)만 싣는다(개념 이름·문제 본문·이메일은 싣지 않음). 아침 알림은 기본 꺼짐(`outreach.morning_alert`), 저녁 알림은 기본 켜짐(`outreach.evening_alert`)이고, 복습할 개념이 없으면 둘 다 보내지 않는다. 저녁 알림은 토요일·일요일(Asia/Seoul)에 보내지 않는다(아침 알림과 새벽 작업은 매일). 알림을 누르면 `https://claude.ai/new`(ntfy `Click` 헤더)를 열어 바로 "복습하자"를 말할 수 있게 한다. 보내지 못하면 작업 실패로 남는다.

**시간 배치 근거:** 저녁에 새 주제를 학습하고, 잠을 잔 뒤, 아침에 인출 연습을 하는 순서다. 수면 중 기억 공고화(Gais et al., 2006), 저녁 학습 → 수면 → 아침 재학습 순서의 효과(Mazza et al., 2016), 테스트 효과(Roediger & Karpicke, 2006), 간격 효과(Cepeda et al., 2006)에 근거한다. 아침이 인출에 특히 좋다는 시간대 효과 자체는 근거가 엇갈리므로, 시각은 설정으로 바꿀 수 있게 둔다.

### 7.5 튜터 교수 규칙

MCP 서버의 `instructions`(연결 시 Claude에 전달)와 튜터용 Claude 프로젝트 지침에 같은 규칙을 둔다. 둘 다 강제는 아니므로, 점수에 영향을 주는 부분(정답 공개, 채점)은 서버가 지킨다.

- 서버 `instructions`(`src/tutor/study/prompts/mcp-instructions.md`)는 서버가 연결된 모든 대화에 전달된다. 학습과 상관없는 대화에서는 도구를 부르지 않게 하고, 도구를 부르는 때·학습 기록 쓰는 법·교수 규칙만 둔다.
- Claude 프로젝트 지침(`docs/claude-project-instructions.md`, 사용자가 프로젝트에 붙여 넣음)은 튜터 프로젝트 안의 대화에만 적용된다. 역할, 진행 방식(대화 시작, 묻는 각도, 내 프로젝트와 연결), 형식을 둔다.
- 퀴즈 규칙(아래 마지막 항목)은 3단계에서 퀴즈 도구와 함께 두 지침에 넣는다.

- 정답을 바로 주지 않는다. 먼저 사용자가 생각을 말하게 하고, 힌트는 단계적으로 준다.
- 설명할 때는 `get_learning_context`로 받은 경험 카드와 연결한다.
- 웹 검색 결과를 쓰면 출처 링크를 단다.
- 사용자가 명시적으로 원하면 답을 보여준다(탈출구). 이때 `record_study_note`에 `answer_revealed = true`로 남기고, 관련 개념은 복습 우선순위에 오른다.
- 퀴즈 중에는 `submit_answer` 전에 정답을 말하지 않는다(서버도 결과 전에는 정답을 주지 않는다).

### 7.6 로컬 MCP 구성

- **SDK:** 공식 TypeScript SDK v2(`@modelcontextprotocol/server`)를 쓴다. v1 `@modelcontextprotocol/sdk`를 잇는 안정 버전이고, 2024-11-05 이후 프로토콜 버전을 모두 협상할 수 있다.
- **연결:** Claude Desktop 설정에 MCP 서버를 등록한다(`claude_desktop_config.json` 또는 `.mcpb` 확장). Desktop이 `node <배포 경로>/dist/mcp-stdio.js`를 띄우고 stdio로 통신한다. 환경 변수(DB 주소, `claude` 실행 파일 경로)는 설정에 넣거나 `.env`에서 읽는다. Desktop이 띄우는 프로세스의 작업 디렉터리는 프로젝트 루트가 아닐 수 있으므로 `.env` 경로를 `GROWTH_ENV_FILE`로 준다.
- **실행 위치:** 개발 중인 작업 트리가 아니라 빌드된 릴리스 디렉터리를 가리킨다. 코드를 고치는 중에 Desktop의 도구가 깨지지 않게 하기 위해서다(배포 방식은 `docs/ops.md`).
- **프로세스:** Desktop이 띄우고 끈다. 시작할 때 DB 마이그레이션은 하지 않고, 마이그레이션이 덜 됐으면 도구가 오류를 돌려준다. 마이그레이션은 배포 때 한다.
- **로그:** 표준출력은 MCP 메시지 통로라 쓰지 않는다. 로그는 `LOG_DIR/mcp`의 회전 파일에 쓴다(상시 실행 앱과 디렉터리를 나눈다). `LOG_DIR`가 없으면 표준에러에 쓴다(Claude Desktop의 MCP 로그에 남는다).
- **도구 설계**
  - 도구 이름은 동사로 시작하고, 설명에 "언제 부르는지"를 쓴다(Claude가 고르는 근거).
  - 입력은 zod 스키마로 정의하고 검증한다.
  - 결과는 Claude가 읽을 짧은 텍스트와 구조화된 내용을 함께 준다. 아직 풀지 않은 문제의 정답은 싣지 않는다.
  - 되돌릴 수 없는 도구(삭제)는 만들지 않는다.
- **단계별 도구**

| 단계 | 도구 |

| 2 | `search_experience`, `list_pending_concepts`, `review_concept`, `list_pending_cases`, `review_case`, `sync_now`, `sync_status` |

| 4 | `get_daily_topic`, `get_weekly_report` |

### 7.7 원격 커넥터와 인증 (4단계, ADR-0035)

- **연결:** Claude 커스텀 커넥터로 등록한다(MCP URL `https://mcp.seok.app/mcp`). 웹에서 추가하면 데스크톱·iOS에서도 쓴다. MCP HTTP 진입점(`mcp-http.ts`, Nest HTTP 앱)이 `/mcp`, OAuth 경로, `/healthz`를 띄우고 `127.0.0.1`에만 바인딩한다. 커넥터 등록은 아직이다.
- **공개 경로:** Cloudflare 이름 있는 터널(`mcp.seok.app` → `127.0.0.1:3100`). 터널은 Host를 그대로 넘기므로 `/mcp`의 Host·Origin 검사는 localhost와 공개 호스트를 받는다.
- **IP 제한 (예정):** Cloudflare WAF 사용자 정의 규칙으로 `/mcp`·`/token`은 Anthropic 외부 요청 대역(`160.79.104.0/21`)만 허용한다. 모든 Claude 사용자가 공유하는 대역이라 인증을 대신하지 못한다. `/authorize`와 구글 콜백·동의는 사용자 브라우저가 열므로 제외한다.
- **역할:** 이 서버가 인가 서버(`/authorize`, `/token`)이자 자원 서버(`/mcp`)다. OAuth 2.1 인가 코드 + PKCE(S256), 클라이언트 식별은 CIMD, 본인 확인은 구글 로그인(OIDC, 범위 `openid email`) + 이메일 허용 목록(`OAUTH_ALLOWED_EMAILS`). 구글 토큰은 신원을 꺼낸 뒤 버린다. 코드는 `core/auth`.

**흐름**

1. **탐색:** Claude가 토큰 없이 `/mcp`를 부르면 `401` + `WWW-Authenticate: Bearer error="invalid_token", …, resource_metadata="https://mcp.seok.app/.well-known/oauth-protected-resource/mcp"`. Claude는 그 보호 리소스 메타데이터(RFC 9728, `resource`가 MCP URL과 정확히 같다, 경로 없는 `/.well-known/oauth-protected-resource`에서도 같은 문서)에서 인가 서버를 찾고, `/.well-known/oauth-authorization-server`(RFC 8414)에서 엔드포인트를 읽는다. `client_id_metadata_document_supported: true`와 `token_endpoint_auth_methods_supported: ["none"]`이 있어 등록(DCR) 대신 CIMD를 쓴다.
2. **`GET /authorize`:** `client_id`(CIMD URL)를 검사한다. https, 허용 호스트(`OAUTH_CLIENT_ID_HOSTS`, 기본 `claude.ai,chatgpt.com`), 포트·사용자 정보·fragment 없음. 그다음 문서를 가져온다(리디렉트 따라가지 않음, 5초, 5KiB). 문서의 `client_id`가 URL과 같고, 공개 클라이언트이고(기본 방식이 아니어도 `token_endpoint_auth_methods_supported`에 `none`이 있으면 받는다, ChatGPT), `redirect_uri`가 문서 목록에 정확히 있어야 한다(루프백 `http://localhost`·`127.0.0.1`·`[::1]`만 포트를 무시, RFC 8252). 여기까지 실패하면 클라이언트로 돌려보내지 않고 오류 화면(400)이다. 처음 보는 client_id와 거절한 client_id는 로그에 남긴다. 그다음 실패(`response_type`이 `code`가 아님, S256 PKCE 없음, `resource`가 MCP URL이 아님)는 redirect_uri에 `error`를 붙여 돌려보낸다. 통과하면 인가 요청을 저장하고 구글로 보낸다(우리 쪽 state·nonce·PKCE S256).
3. **`GET /oauth/google/callback`:** state로 요청을 찾고(한 번만), 구글 코드를 토큰으로 바꿔 id_token을 검증한다(구글 공개 키 서명, `iss`, `aud`=우리 구글 client_id, `exp`, nonce). `email_verified`이고 이메일이 허용 목록에 있으면 동의 화면을 그린다. 아니면 요청을 지우고 403 오류 화면. 사용자가 구글 로그인을 취소했으면 `access_denied`로 돌려보낸다.
4. **동의 화면, `POST /oauth/consent`:** 클라이언트 이름(CIMD `client_name`), client_id URL, 돌아갈 호스트, 로그인한 이메일을 보여 주고 "방금 내가 시작한 연결이 아니면 거절"을 안내한다. 콜백 주소가 모든 Claude 사용자에게 같아서, 남이 자기 Claude에 이 서버를 추가해 만든 로그인 링크를 내가 누르면 구글 자동 로그인으로 조용히 통과할 수 있기 때문이다. 폼에는 요청마다 새로 만든 값(`consent_token`)을 숨겨 넣어 다른 사이트가 대신 제출하지 못하게 하고(CSRF), 화면은 iframe에 넣지 못하게 한다(`frame-ancestors 'none'`). 허용이면 1회용 인가 코드를 만들어 `redirect_uri?code&state&iss`로(303), 거절이면 `error=access_denied`로 보낸다. 같은 동의 값은 다시 쓸 수 없다.
5. **`POST /token`** (form-urlencoded, 응답 `Cache-Control: no-store`, 오류는 RFC 6749 JSON):
   - `authorization_code`: 코드를 꺼내며 지우고(1회용), 만료·client_id·redirect_uri·PKCE(`code_verifier`의 S256이 저장한 challenge와 같음)·resource를 본다. 하나라도 틀리면 `invalid_grant`(resource는 `invalid_target`). 통과하면 토큰 계열을 열고 액세스 토큰(1시간)과 리프레시 토큰(90일)을 준다.
   - `refresh_token`: 아직 회전하지 않은 토큰이면 회전 표시를 하고(조건부 UPDATE라 동시에 와도 하나만 통과) 같은 계열에 새 쌍을 준다. 새 리프레시 토큰은 다시 90일이다. 이미 회전한 토큰이 다시 오면 탈취로 보고 그 계열을 폐기하고(그 계열의 액세스·리프레시 토큰이 모두 막힌다) `AdminNotifier`로 알린 뒤 `invalid_grant`. 만료·폐기된 토큰도 `invalid_grant`라 Claude가 다시 로그인을 띄운다.
6. **`/mcp`:** Host·Origin 검사(403) 뒤 Bearer 토큰을 본다. 없거나, 모르거나, 만료됐거나, 폐기된 계열이거나, 다른 resource를 위한 토큰이면 1번과 같은 `401`. Claude는 `401`을 받으면 리프레시한다.

- **로그:** 토큰·코드·시크릿·state는 남기지 않는다. 거절 이유, 처음 보는 client_id, 허용·거절한 이메일은 남긴다.
- **상시 실행:** LaunchAgent(`com.growthassistant.server`, `ops/install.sh`)가 배포 릴리스의 `dist/mcp-http.js`를 띄운다. `KeepAlive`로 죽으면 10초 간격으로 다시 띄우고, 배포가 새 릴리스로 바꾼 뒤 `kickstart -k`로 다시 띄운다. FileVault 유지(재부팅 뒤 로그인해야 뜸). 운영 방법은 `docs/ops.md` "상시 실행"·"OAuth".
- **운영 알림:** `AdminNotifier.notify(종류, 자세한 내용)`. 자세한 내용은 로그(`[관리 알림]`)에만 남기고, `NTFY_TOPIC`이 있으면 ntfy 토픽(`NTFY_URL`, 기본 `https://ntfy.sh`)으로 휴대폰에 제목(종류)·시각·건수만 보낸다(공용 서버를 평문으로 지나가므로 이메일·토큰 계열 ID는 보내지 않는다). 종류는 리프레시 토큰 재사용으로 연결 폐기(탈취 의심이라 우선순위 `urgent`, 나머지는 `high`), 허용되지 않은 계정(허용 목록 밖이거나 구글 미확인 이메일)의 로그인 시도, Claude CLI 인증 오류, 예약 작업 실패(`SCHEDULED_JOB_FAILED`, ADR-0036)다. 서버 시작·재시작과 일반 도구 오류는 알리지 않는다. 같은 종류는 1시간에 한 번만 보내고 그 사이 건수는 다음 알림에 "외 N건"으로 붙인다(프로세스 메모리, 재시작하면 초기화). 전송 실패(5초 타임아웃)는 로그만 남기고 원래 요청은 그대로 처리한다. 서버 다운은 외부 헬스체크(UptimeRobot, `/healthz`, 5분 간격)가 알린다. 학습 알림은 같은 토픽의 다른 종류다(7.4 "5단계 구현").
- **화면 (6단계):** MCP Apps로 객관식·확신도 버튼, 숙련도 3단계 색 표시, 응답 시간 측정을 검토한다(iOS는 WKWebView로 지원).

## 8. 숙련도와 약점 추적

### 원칙

- 숙련도는 **힌트 없이, 확신을 갖고 답한 응답**으로만 인정한다. 연습 점수가 실력처럼 보이는 착시를 피하기 위해서다.
- Claude는 숙련도를 직접 판단하지 않는다. 객관식·빈칸은 코드가 채점하고, 오개념은 출제할 때 오답 보기에 붙여 둔 것을 기록한다. 점수 계산도 코드가 한다.

### 응답 → FSRS 등급 매핑

| 응답 | FSRS 등급 |
|---|---|
| 오답 | Again |
| 정답 + 찍음, 또는 힌트 사용 | Hard (숙련도 계산에서는 정답으로 세지 않음) |
| 정답 + 애매 | Good (숙련도 계산에서는 0.5점) |
| 정답 + 확실 + 빠른 응답 (응답 시간이 없으면 정답 + 확실) | Easy |
| 오류 신고된 문제 | 반영하지 않음 |

### 약점 점수

힌트 없이 낸 응답만 반영한다. 힌트를 쓴 응답은 FSRS 일정만 바꾼다 (ADR-0028).

```
credit  = 정답이면 확실 1, 애매 0.5, 찍음 0. 오답은 0
penalty = 오답일 때만: 확신했으면 +0.5, 같은 오개념이 전에도 나왔으면 +0.5
mastery_score  = EMA(credit)                       -- 힌트 없는 응답의 최근 가중 정답률
weakness_score = min(1, EMA(1 − credit + penalty)) -- (1 − 숙련도) + 확신한 오답·반복 오개념 가산점
EMA(x) = 첫 응답이면 x, 그 뒤로 0.4·x + 0.6·이전 값  (최근 4~5번이 대부분을 정함)
  · 채점된 시도가 2회 미만 → "미측정" (약점과 구분)
  · weakness_score ≥ 0.5 → 약점
```

- 같은 오개념이 반복됐는지는 풀이 기록을 가진 `quiz`가 판단해 `MasteryService.recordAnswer`에 넘긴다. `mastery`는 퀴즈 테이블을 모른다.
- 공식은 응답을 순서대로 접는 순수 함수(`applyAnswer`)다. 문제가 신고되면 그 개념의 풀이 기록에서 신고된 문제의 풀이를 빼고 처음부터 다시 접어 점수와 일정을 바꾼다(`report_question`과 함께 구현).

- **근본 원인 추적 (ADR-0031):** 약점 개념의 선수 개념(`PREREQUISITE`)을 3단계까지 거슬러 올라가, 약점 개념 둘 이상이 기대고(ADR-0033) 그 자신이 약점·미측정·다룬 적 없음인 개념을 근본 원인 후보로 표시한다. 기대는 약점 개념이 많은 것부터다. 근본 원인 후보는 저녁 주제와 출제에서 최우선 순위가 된다(출제에서는 오늘 이미 푼 후보를 뺀다).
- **`get_weakness` 도구 (`quiz` 모듈, ADR-0031):** 트랙별 약점 상위 3개(숙련도, 약점 점수, 채점 수, 다음 복습일, 두 번 이상 고른 오개념), 근본 원인 후보, 미측정 개념 수를 돌려준다. 지난주 대비 변화는 6단계 주간 리포트와 함께 숙련도 이력을 만들 때 더한다.

## 9. 오류 처리

운영 문제는 로그 파일에 남기고, 그중 운영자가 바로 알아야 할 것은 운영 알림(ntfy, 7.7 "운영 알림")으로 보낸다. 사용자가 알아야 할 것은 도구 결과(대화 중 Claude가 전달)와 주간 리포트로 보여 준다.

### `claude` CLI

- **인증 만료:** 출력에서 인증 오류를 감지하면 로그에 남기고, 그 뒤 도구 결과에 "맥미니에서 `claude` 다시 로그인 필요"를 함께 돌려준다. Claude를 쓰는 서버 예약 작업은 멈추고, 다시 로그인하면 재개한다.
- **사용량 한도 도달:**
  - 급하지 않은 작업(문제 풀 보충, 추출)은 한도가 풀릴 때까지 미룬다.
  - 퀴즈는 미리 만든 문제로 계속한다. 채점은 LLM을 쓰지 않으므로 영향이 없다. 풀에 문제가 없으면 즉석 생성이 실패하고, 도구가 그 이유를 돌려준다.
  - Claude 앱의 대화도 같은 구독 한도를 쓴다. 한도에 걸리면 Claude 앱이 안내한다.
- **타임아웃:** 1회 재시도한다.
- **JSON 형식 오류:** 1회 재요청하고, 그래도 실패하면 실패로 기록한다.

### Mac 잠자기와 놓친 실행

- 맥미니가 잠들면 서버 예약 작업과 5단계의 Claude 예약 작업이 돌지 않는다. 잠자기 방지(`pmset`)는 설정했고 운영 가이드에 기록했다.
- 서버 예약 작업의 실행 여부는 작업 실행 기록(`scheduled_job.slot_date`)으로 판단해 중복 실행을 막는다.
- 놓친 서버 작업은 그날(Asia/Seoul) 안에 서버가 뜨면 한 번 실행하고, 날이 바뀌면 건너뛴다. 서버가 뜬 채 잠자기로 시각을 넘기면 크론 타이머가 깨어난 뒤 늦게 울릴 수 있는데, 그때도 같은 규칙(오늘 시각이 지났고 오늘 몫을 안 돌렸을 때만)으로 판단한다.
- Claude 예약 작업(5단계)은 그때 고른 방식의 규칙을 따른다. 같은 날 두 번 불려도 `outreach_log`로 같은 내용을 돌려준다.

### 수집

- 문서 단위로 실패를 격리하고, 실패한 문서는 다음 실행 때 재시도한다.
- Notion 호출 속도를 제한한다.

### MCP 프로세스

- DB가 꺼져 있거나 마이그레이션이 덜 됐으면 도구가 원인을 담은 오류를 돌려준다. Claude가 대화에서 그대로 전달한다.
- 처리하지 않은 예외로 프로세스가 끝나면 Desktop이 도구를 쓸 수 없다고 표시한다. 도구 처리기 진입점에서 예외를 모두 잡아 오류 결과로 바꾼다.

## 12. 범위 밖 (후속 과제)

- **서술형 문제 (ADR-0019로 미룸).** 객관식·빈칸 품질을 확인한 뒤 설계한다.
  - 판단형: 제약이 있는 상황을 주고 "무엇을 고르고 왜, 무엇을 포기하나"를 묻는다. 결론보다 근거를 본다.
  - 면접형: 내 경험을 먼저 설명하게 한 뒤 경험 카드(STAR+L)와 비교해 빠진 요소를 피드백한다.
  - 채점 기준표(예: 제약 파악, 대안 비교, 트레이드오프 명시, 결론과 근거의 일관성, 내 경험 연결)를 문제와 함께 저장하고, `claude -p`가 항목별로 채점한다. 검증은 "정답이 하나뿐인가" 대신 "기준표만으로 채점할 수 있는가"를 본다.
  - 사용량 한도에 걸리면 채점을 보류하고 나중에 채점한다.
- `career` 모듈: 이력서·포트폴리오 수정, Canva 연동 (같은 MCP 서버에 도구로 추가하는 방식을 검토)
- 임베딩 기반 하이브리드 검색 (pgvector, 로컬 임베딩 모델)
- GitHub 등 추가 기억 출처
- FSRS 파라미터 최적화 (복습 기록이 수백 건 쌓인 뒤)
- 문제 생성 같은 백그라운드 작업을 Claude 예약 작업으로 옮겨 `claude -p`를 줄일지 검토
