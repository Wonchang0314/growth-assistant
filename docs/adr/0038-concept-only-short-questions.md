# ADR-0038: 문제는 경험을 싣지 않은 개념 문제로만 짧게 내고, 숙련도에 따라 깊이를 올리며, 판단 사례 추상화는 새벽 작업에서 뺀다

- 상태: 채택
- 날짜: 2026-10-20
- ADR-0021의 "판단 사례로 상황 판단형 객관식을 낸다", ADR-0029 출제 재료의 "관련 경험 카드 3장", ADR-0032 전체(출제 순서, `[가정한 상황]` 머리말, 채점 결과의 경험 표현), ADR-0033 3절(개념 2 : 상황 판단형 1), ADR-0036 2절의 새벽 작업 "판단 사례 추상화" 단계를 바꾼다. 판단 사례 자체(추상화·검토 도구·`npm run abstract`, ADR-0021·0024·0026)와 변형 문제, 검증 흐름(ADR-0029의 한 번 다시 쓰기)은 그대로다.

## 맥락

원격 커넥터와 예약 작업으로 실제로 복습을 풀기 시작했다(ADR-0034). 문제 풀의 VALID 문제를 보니 상황 판단형 질문은 평균 440자(최대 500자), 개념 문제 중 동작 원리는 평균 179자(최대 308자)였다. 사용자 의견(2026-10-20):

1. 경험에서 만든 상황 판단형은 너무 길다. 가볍게 시작해서 깊이 들어가고 싶은데 첫 문제부터 지친다.
2. 회사 맥락과 도메인 용어를 걷어내도 원래 상황이 떠올라 답이 짐작된다. 개념 문제도 출제 프롬프트에 경험 카드 3장을 실어 같은 일이 생길 수 있다.
3. 경험에서는 기술 키워드·개념만 가져오고, 문제는 완전히 새로 만들고 싶다.

## 결정

1. **문제는 개념 문제(왜·언제 쓰나·트레이드오프·동작 원리)로만 낸다.** 판단 사례로 상황 판단형(`SCENARIO`)을 만들거나 내지 않는다. 짧은 가상 상황은 써도 되지만, 출제 프롬프트에는 경험 카드·판단 사례를 싣지 않는다. 경험은 어떤 개념을 낼지 고르는 데(개념 그래프, 숙련도, 학습 기록)만 쓴다.
2. **길이 상한을 둔다.** 질문은 2문장·150자 안, 객관식 보기는 하나에 40자 안이다. 출제 프롬프트에 싣고, 출제 직후 코드의 모양 검사(`draftProblems`)가 같은 상한으로 본다. 넘으면 검증에 걸린 것으로 보고 이유를 붙여 한 번 다시 쓴다(ADR-0029). 글자는 화면에 보이는 글자 단위(한글 음절 하나가 한 글자), 문장은 마침표·물음표·느낌표 뒤가 공백이나 끝인 곳에서 센다.
3. **숙련도에 따라 깊이를 올린다(가볍게 시작해서 딥다이브).** 각도는 생성 모델이 아니라 코드(`nextAngle`)가 숙련도(ADR-0028)로 정한다.

   | 숙련도 | 각도 |
   |---|---|
   | 일정 없음, 미측정(채점 2회 미만), 약점(약점 점수 0.5 이상) | 동작 원리(MECHANISM): 짧은 정의·원리 확인 |
   | 양호, 숙련도 점수 0.8 미만 | 왜(WHY)·언제 쓰나(WHEN) 중 그 개념에서 덜 낸 쪽 |
   | 숙련도 점수 0.8 이상 | 트레이드오프(TRADEOFF)·설계 판단 |

   변형 문제도 같은 각도를 쓴다. 핵심은 원래 문제와 같고 상황·조건만 바꾼다.
4. **문제 풀을 정리한다(마이그레이션 `0013_concept_only_quiz`, 배포 때 적용).**
   - 상황 판단형 중 풀이 기록(`quiz_attempt`)이 없고 다른 문제가 변형(`variant_of`)으로 가리키지 않는 문제는 지운다.
   - 풀이 기록이 있는 상황 판단형(지우면 FSRS·숙련도 이력이 사라진다)과 다른 문제가 변형으로 가리키는 상황 판단형(FK로 지울 수 없다)은 지우지 않고 INVALID로 둔다(이미 INVALID면 사유도 그대로).
   - 길이 상한을 넘는 VALID 문제는 INVALID로 둔다. 사유(`validation_note`)는 "ADR-0038: …"이다.
   - 조건으로 지우고 바꾸며 id를 박지 않는다. 운영 DB(2026-10-20)에서는 상황 판단형 13개 중 풀이가 있는 3개가 INVALID로 남고 10개가 지워진다.
   - 낼 문제가 없어진 개념은 새벽 작업(오늘 복습할 개념 중 낼 문제가 없는 개념)과 복습 세트의 뒤에서 만들기가 새 문제로 채운다.
5. **채점 결과의 관련 경험 한 문장은 남긴다.** 출제 프롬프트에는 싣지 않은 그 개념의 경험 카드 하나(맞은 개념이 많은 것, 최근 것 순)를 코드가 문제에 잇고, 채점 결과에 "같은 개념을 다룬 내 경험: <카드 제목>"으로 보여 준다. "이 원칙을 실제로 겪은 경험"은 경험 사례로 만든 옛 상황 판단형에만 쓴다.
6. **새벽 작업에서 판단 사례 추상화를 뺀다.** 새벽 작업은 동기화 → 추출 → 문제 미리 만들기다. 이미 만든 판단 사례, 검토 도구(`list_pending_cases`, `review_case`), `npm run abstract`는 남긴다. 판단 사례를 다시 쓸 일(서술형 면접 연습 등)이 생기면 그때 정한다.
7. 쓰지 않게 된 코드(상황 판단형 출제 순서, 상황 판단형 출제 프롬프트, `[가정한 상황]` 머리말, 개념별 승인 사례 조회)는 지운다. `angle`의 `SCENARIO` 값과 `case_id` 열은 남은 옛 문제 때문에 둔다.

## 결과

- 좋은 점
  - 첫 문제가 짧고 가볍다. 개념을 익힐수록 같은 개념에서 더 깊은 질문이 나온다.
  - 문제에 내 상황이 비치지 않아 기억이 아니라 이해로 푼다. 회사 맥락이 문제로 샐 길도 줄어든다.
  - 새벽 작업의 구독 사용량이 줄어든다(추상화 호출이 없다).
- 나쁜 점·감수할 것
  - 실전 판단(상황 판단형) 연습이 없어진다. 트레이드오프 각도가 일부를 대신하지만 숙련도가 높은 개념에서만 나온다.
  - 만든 판단 사례 271개를 지금은 쓰지 않는다.
  - 길이 상한이 엄격해 VALID 비율이 떨어질 수 있다. 다시 쓰기는 여전히 한 번이다.
  - 숙련도 경계(0.5·0.8)와 각도 대응은 써 보고 조정할 수 있다.
  - 채점 결과의 경험 카드는 문제와 개념만 같을 뿐 문제의 핵심과 맞지 않을 수 있다.

## 검토한 대안

- **상황 판단형을 짧게만 줄이기:** 길이는 해결하지만, 원래 상황이 떠올라 답이 짐작되는 문제는 남는다.
- **경험 카드를 키워드만 뽑아 출제 프롬프트에 싣기:** 개념 그래프가 이미 그 역할(경험에서 나온 개념)을 하고, 키워드가 다시 상황을 끌어올 수 있다.
- **길이를 검증 모델(Opus)에게 맡기기:** 호출이 늘고 기준이 흔들린다. 글자 수는 코드가 정확히 센다.
- **기존 상황 판단형을 모두 INVALID로만 두기:** 풀이 기록이 없는 문제까지 남길 이유가 없어, 이력이 없는 문제는 지우기로 했다(사용자 결정).
