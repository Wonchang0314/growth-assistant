# ADR-0021: 학습 트랙에 IT 인프라를 더하고 가중치를 다시 나누며, 업무 경험은 회사 맥락을 걷어낸 판단 사례로 바꿔 상황 판단형 객관식으로 낸다

- 상태: 일부 대체됨 (1절 학습 트랙과 가중치 → ADR-0022)
- 날짜: 2026-10-16

## 맥락

시드 개념을 정하려고 2026-10-16에 Notion `복습` 아래 문서를 서브에이전트로 모두 읽고 개념 후보를 뽑았다. 대상은 GIS 프로젝트 복습 문서 145개, Spring 필독서, git 이력 관리, 프런트엔드 면접 109제다. 후보는 상위 개념 약 100개, 하위까지 약 400개다([후보 목록](../research/2026-10-16-seed-concept-candidates.md)). 이 과정에서 세 가지가 드러났다.

1. **취업·면접 트랙 개념이 두 종류다.** "null(모름)과 0(없음)을 구분한다", "컬럼은 배포 전에 추가하고 배포 후에 지운다" 같은 **판단 원칙**은 일반화할 수 있는 기술 지식이다. "트레이드오프 설명", "장애 회고" 같은 **설명 능력**은 서술형으로만 채점할 수 있다(ADR-0019로 미룸). 설계의 1순위 트랙(가중치 0.4)이 사실상 서술형에 묶여 있었다.
2. **업무 문서로 문제를 만들면 회사 맥락에 묶인다.** 복습 문서는 회사 테이블, 사내 데이터 원천, 업무 규칙 위에서 쓰였다. 그대로 문제로 만들면 회사 사정을 기억해야 풀 수 있다. 회사 고유 이름이 문제와 DB에 남기도 한다. 또 회사에서 내린 결정은 그 회사의 제약에서 나온 것이라 일반적인 정답이 아닐 수 있다. 실제로 문서 여러 편에 결정을 되돌린 기록이 있다. 설계 7.3의 "내 프로젝트 문제"(`MY_PROJECT`) 객관식("이 프로젝트에서 X 대신 Y를 고른 이유는?")도 같은 문제를 안고 있다.
3. **인프라 개념이 많고 실수도 가장 많이 몰려 있다.** Docker, nginx, CI/CD, 인증서, DNS, PostgreSQL 운영 개념이 60개가 넘는다. peer 인증 오추론, 컨테이너 안의 localhost, DNS 문제를 인증서 문제로 본 오진, SSH 키 사고 같은 실수 기록도 여기에 가장 많다. 그런데 지금 트랙에는 이를 담을 곳이 없어 백엔드와 CS 기초에 흩어진다.

## 결정

### 1. 학습 트랙

| 트랙 | 가중치 | 범위 |
|---|---|---|
| CS 기초 | 0.3 | 원리: 네트워크, OS, DB 이론(트랜잭션·인덱스 원리), 자료구조·알고리즘, 계산 기하, 수치·통계 |
| 백엔드 | 0.3 | 애플리케이션: Spring·NestJS, TypeScript(서버), JPA, 캐시, API·데이터 모델링, PostgreSQL 사용(쿼리·인덱스·마이그레이션), 배치·데이터 통합, 테스트 |
| 프론트 심화 | 0.2 | 지금 쓰는 스택: JS/TS, React, Vite(Rollup), TanStack Query, 상태관리, 브라우저 렌더링·성능, WebGL 렌더링 |
| IT 인프라 | 0.2 | 구성·운영·진단: Docker, nginx, CI/CD, 인증서·DNS 운영, 방화벽·VPN 진단, 리눅스 운영, PostgreSQL 운영(인증·백업), 배포 구성 |
| 취업·면접 | 0 | 설명 능력(내 경험·트레이드오프를 말로 설명하기). 서술형을 만들 때 가중치를 다시 준다 |

- **경계:** 개념 하나는 트랙 하나에만 속한다. CS 기초는 "왜 그렇게 동작하나", IT 인프라는 "어떻게 구성하고 고장을 진단하나"를 맡는다. 예를 들어 TLS 핸드셰이크는 CS 기초, ACME 인증서 발급은 IT 인프라다. 트랙에 걸친 관계는 `PREREQUISITE`·`RELATED` 간선으로 잇는다. 그러면 인프라 문제를 계속 틀릴 때 근본 원인 추적(설계 8장)이 CS 쪽 원리까지 거슬러 올라간다.
- **판단 원칙은 기술 트랙의 개념이다.** 그 지식이 속한 트랙(주로 백엔드·프론트 심화)에 둔다. 판단 원칙이라는 개념 종류 컬럼은 따로 두지 않는다.
- 가중치는 새 개념을 고를 때(설계 7.3의 우선순위 ③)에만 쓰인다. 써 보고 조정한다.

### 2. 상황 판단형 문제 (`angle = SCENARIO`)

- 유형은 객관식이다. 코드가 채점하는 원칙(ADR-0019)을 그대로 지킨다. 빈칸과 서술형으로는 내지 않는다.
- 문제는 가상의 상황과 조건을 주고 판단을 묻는다. 질문 틀은 좁게 잡는다. 예: "가장 먼저 확인할 것은?", "이 선택의 가장 큰 위험은?", "이 조건에서 가장 적절한 순서는?"
- **정답의 근거는 일반 원칙이다.** "회사에서 이렇게 했다"는 정답의 근거가 아니다. 정답이 하나로 정해지도록 상황에 조건을 명시한다(예: "다운타임 불가", "배포 중 구버전 앱이 함께 떠 있음").
- 오답 보기는 당시 내가 실제로 했던 틀린 판단으로 만든다. 문서에 실수 기록이 없으면 흔한 오개념으로 만든다.
- `MY_PROJECT` 객관식은 내지 않고 `SCENARIO`로 대신한다. `MY_PROJECT`는 내 경험을 말로 설명하는 서술형 면접 연습에 남긴다(서술형과 함께 미룸).

### 3. 판단 사례: 수집 단계에서 한 번 추상화한다

- 경험 카드(STAR+L)를 추출할 때 판단이 들어 있는 경험에서 **판단 사례**도 함께 뽑아 저장한다. 경험 카드는 "내 이야기"이고, 판단 사례는 그 이야기에서 회사 맥락을 걷어낸 버전이다.
- 판단 사례는 구조화 필드로 받는다. 필드는 상황, 제약, 선택지(고른 것과 고르지 않은 이유), 결정, 근거, 결과, 불변 조건, 연결 개념이다. **불변 조건**은 도메인을 바꿔도 반드시 남아야 하는 사실이다(예: "원천 테이블은 기존 행을 제자리에서 UPDATE한다").
- 문제는 판단 사례에서 만든다. 같은 사례를 다른 도메인으로 바꿔 변형 문제(`key_point`, `variant_of`)를 낸다.

### 4. 세 단계 게이트

판단 사례와 그 사례로 만든 문제는 모두 다음 순서를 통과해야 쓴다.

1. **치환 (LLM):** 회사 고유 용어를 지우지 않고 역할 설명으로 바꾼다. 예: 사내 고객 테이블 이름 → "고객 확장 정보 테이블". 용어 사전을 프롬프트에 함께 넣는다.
2. **금지어 게이트 (코드, 결정적):** 정규식으로 검사하고 통과·거부만 한다. 고쳐 쓰지 않는다. 검사 대상은 용어 사전의 용어, IP 주소, 사내 도메인·URL, `UPPER_SNAKE` 테이블명 같은 패턴이다. 걸리면 걸린 용어를 붙여 1회 다시 생성한다.
3. **독립 검증 (LLM, 별도 호출):**
   - 판단 사례: 원문과 추상화본을 함께 주고 묻는다. 같은 근거로 같은 결론이 나오는가, 불변 조건이 모두 살아 있는가.
   - 문제: 정답을 주지 않고 문제만 보고 풀게 한다. 정답을 맞히지 못하거나, 모르는 용어가 있다거나 정보가 부족하다고 답하면 실패다. 기존 검증(정답이 하나인가 등, 설계 7.3)도 함께 한다.

실패하면 1회 다시 생성한다. 그래도 실패하면 판단 사례는 `PENDING`으로, 문제는 `INVALID`로 둔다.

### 5. 검토와 용어 사전

- 개념 승인 정책(ADR-0007)과 같은 구조로 검토한다. 게이트를 통과한 판단 사례는 바로 `ACTIVE`가 되고, 걸린 것만 `PENDING`으로 남는다. `PENDING` 사례는 Claude 앱 대화에서 도구(`list_pending_cases`, `review_case`)로 승인·수정·거절한다. 자동 승인된 사례는 주간 리포트에서 사후 확인한다(4단계).
- 용어 사전(회사 고유 용어 → 일반 표현)은 레포에 두지 않고 DB에 둔다. 회사 고유 이름을 코드 저장소에 남기지 않기 위해서다. 등록 방법은 2단계 구현 때 정한다.

## 결과

- 좋은 점
  - 면접 대비 목표를 서술형을 기다리지 않고 판단형 객관식으로 바로 연습한다. 채점은 계속 코드가 즉시 한다.
  - 문제가 회사 사정을 몰라도 풀리고, 회사 고유 정보가 문제·로그·대화에 퍼지지 않는다.
  - 추상화를 사례당 한 번만 해서 출제마다 추론 비용과 지연이 들지 않는다. 사람이 검토할 지점도 하나로 모인다.
  - 같은 원칙을 여러 도메인으로 바꿔 물어, 문제 답을 외워 푸는 것을 막고 전이를 돕는다.
  - 인프라 약점이 백엔드 숙련도에 섞이지 않고 따로 보인다.
- 나쁜 점·감수할 것
  - 불변 조건을 지키는지, 정답이 하나인지는 결국 LLM 검증에 기댄다. 평가 세트(설계 10장)와 `report_question` 신고로 보완한다.
  - 수집 단계에 추출 호출이 늘어난다(판단 사례 추출, 독립 검증). 백필 때 사용량을 더 쓴다.
  - 판단형 객관식은 보기가 모두 그럴듯해 정답이 갈리기 쉽다. 조건 명시와 독립 풀이 검사로 거르고, 걸러진 만큼 문제 풀이 덜 찬다.
  - 용어 사전이 비어 있거나 낡으면 금지어 게이트가 새 회사 용어를 놓친다. 패턴 검사와 독립 풀이 검사가 뒤에서 받친다.
  - 트랙이 다섯이 되어 경계를 정하는 판단이 늘어난다. 개념 하나 = 트랙 하나 규칙과 간선으로 정리한다.

## 검토한 대안

- **출제할 때마다 원문에서 바로 탈맥락화:** 구현은 가장 단순하다. 하지만 문제마다 추론 비용과 지연이 들고, 탈맥락화 품질이 문제마다 달라지며, 사람이 검토할 지점이 없다.
- **취업·면접 가중치를 유지하고 판단형 문제 비율로 맞추기:** 트랙과 문제 유형이 섞여 숙련도 리포트에서 무엇이 약한지 흐려진다.
- **인프라를 백엔드·CS 기초에 그대로 두기:** 트랙 수는 적지만, 실수가 가장 많은 영역의 약점이 다른 트랙에 묻힌다.
- **금지어를 LLM으로만 거르기:** 결정적이지 않아 아는 용어도 놓칠 수 있다. 알려진 용어는 코드로 확실히 막고, 모르는 용어는 독립 풀이 검사로 잡는다.
- **회사 용어를 지우기만 하기:** 문장이 이해되지 않아 자기완결성이 깨진다.
- **판단형을 서술형으로:** 판단력 검증에는 더 좋지만 채점 기준표와 LLM 채점이 필요하다(ADR-0019로 미룸).
