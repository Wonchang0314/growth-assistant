# ADR-0024: 판단 사례 추상화에 회사 용어 목록을 쓰지 않고, 모양 패턴 검사와 독립 검증으로 회사 맥락을 걸러낸다

- 상태: 채택
- 날짜: 2026-10-17
- ADR-0021의 4절 중 용어 사전을 쓰는 부분(1단계 치환의 용어 사전, 2단계 금지어 게이트의 용어 사전 검사)과 5절의 용어 사전을 대체한다. 판단 사례의 구조, 세 단계 게이트의 순서, 검토 방식은 그대로다.

## 맥락

ADR-0021은 회사 고유 용어 → 일반 표현 목록(`domain_term`)을 DB에 두고, 추상화 프롬프트에 넣고, 금지어 게이트가 그 목록으로 검사하게 했다. 수집한 문서 164개로 목록을 만들어 보니(코드 후보 715개 → Claude 제안 135개) 두 가지가 드러났다.

1. **목록이 프로젝트마다 늘어난다.** 사내 테이블·컬럼·코드값·서버 주소·클래스 이름까지 들어가 문서가 늘 때마다 검토할 목록도 함께 늘어난다.
2. **일반 단어가 섞인다.** 상태값(MAPPED, BASELINE), 업계 약어(B2B, O2O, Tier)는 회사에서 쓰는 말이지만 일반 단어이기도 해서, 금지어로 두면 평범한 설명까지 걸린다.

그리고 이 목록이 막으려던 것을 다시 보면, 문제를 보는 사람은 사용자 한 명이고 DB는 로컬이며 원문은 추출 때 이미 Claude에 간다. 목록이 실제로 지키는 것은 유출보다 "회사 사정을 알아야 풀리는 문제"를 막는 품질이다.

## 결정

- 회사 용어 목록(`domain_term`)과 등록 도구를 만들지 않는다.
- **1단계 치환 (LLM):** 목록 없이, 특정 조직을 가리키는 이름(회사·고객사·협력사, 사내 시스템·DB·테이블·컬럼·코드값, 서버 주소)을 모두 역할 설명으로 바꿔 일반 상황으로 고쳐 쓰게 한다.
- **2단계 게이트 (코드, 결정적):** 목록 없이 모양으로 잡히는 것만 검사한다. IP 주소, URL·도메인, `UPPER_SNAKE` 식별자. 걸리면 걸린 문자열을 붙여 1회 다시 생성한다.
- **3단계 독립 검증 (LLM, Opus, 별도 호출):** ADR-0021의 질문(같은 근거로 같은 결론인가, 불변 조건이 살아 있는가)에 더해 "회사 밖 사람이 이 사례만 보고 이해할 수 있는가, 특정 조직을 가리키는 이름이 남았는가"를 묻는다.
- 검토(`list_pending_cases`, `review_case`)는 그대로다. 검토하다 같은 이름이 거듭 새어 나오면 그때 예외 목록을 다시 검토한다.

## 결과

- 좋은 점: 관리할 목록이 없어 문서가 늘어도 할 일이 늘지 않는다. 일반 단어가 금지어로 걸려 사례가 거부되는 일이 없다. 검증이 "단어가 남았나"가 아니라 "회사 밖 사람이 풀 수 있나"를 직접 본다.
- 나쁜 점·감수할 것: 이름이 남지 않는다는 보장이 코드가 아니라 LLM 판정에 기댄다. 모양 패턴에 걸리지 않는 고유명(한글 회사 이름, 소문자 테이블명)은 3단계가 놓치면 남는다. 자동 승인된 사례의 사후 확인(4단계 주간 리포트)과 사용자 검토로 보완한다.

## 검토한 대안

- 용어 목록 유지(ADR-0021): 목록이 프로젝트마다 늘고 일반 단어가 섞여 관리 비용이 크다.
- 이번에 만든 135개만 등록하고 더 늘리지 않기: "목록에 있는 것"과 "목록 밖이라 LLM 판정에만 기대는 것"이 섞여 규칙이 둘이 된다.
