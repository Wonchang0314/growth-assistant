# ADR-0016: FSRS는 ts-fsrs 라이브러리를 쓰고, 복습 단위는 개념으로 유지한다

- 상태: 채택
- 날짜: 2026-10-14

## 맥락

ADR-0008은 FSRS를 Kotlin으로 직접 포팅하기로 했다. Kotlin 구현인 FsrsKt가 GPL-3 라이선스였기 때문이다. NestJS + TypeScript로 전환하면서(ADR-0014) 선택지가 바뀌었다. FSRS 코드는 아직 작성하지 않았다(3단계 작업).

TypeScript에는 py-fsrs를 관리하는 open-spaced-repetition 조직의 공식 구현 `ts-fsrs`가 있고, MIT 라이선스다.

## 결정

- 알고리즘은 FSRS를 쓰고, 구현은 `ts-fsrs` 라이브러리를 쓴다. 기본 파라미터로 시작한다.
- `ts-fsrs`는 `core`가 아니라 `tutor/mastery` 안의 어댑터 하나에서만 부른다. 나머지 코드는 이 프로젝트의 FSRS 상태 타입(설계 문서 5.3)만 안다.
- 복습 단위는 문제가 아니라 개념이다. 복습할 때마다 같은 개념의 다른 문제를 낸다 (ADR-0008 그대로).
- 하루 복습은 최대 10문제로 제한한다 (ADR-0008 그대로).
- 응답 → FSRS 등급 매핑과 숙련도 계산은 이 프로젝트 코드가 한다 (ADR-0009, 설계 문서 8장).

## 결과

- 좋은 점: 포팅과 기준 값 검증 작업이 없어진다. 공식 구현이라 알고리즘 버전이 바뀌어도 라이브러리 업데이트로 따라간다. 파라미터 최적화 기능도 같은 조직의 도구로 이어 쓸 수 있다.
- 나쁜 점·감수할 것: 라이브러리 버전이 바뀌면 일정 계산 결과가 달라질 수 있어 버전을 고정하고, 대표 시나리오 몇 개는 기대 값 테스트로 남긴다. FSRS가 카드 단위로 설계되어 개념 단위 복습에서 난이도 편차가 생기는 점은 ADR-0008과 같이 감수한다.

## 검토한 대안

- 직접 구현: 알고리즘을 공부하는 데는 좋지만, 이 프로젝트의 우선 목표는 백엔드 개념이다.
- SM-2: ADR-0008과 같은 이유(낮은 예측 정확도)로 제외한다.

## 재검토 조건

복습 기록이 수백 건 쌓이면 사용자 기록으로 FSRS 파라미터를 최적화한다.
