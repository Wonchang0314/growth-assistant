# ADR-0022: 시드 개념을 앞으로 배울 커리큘럼으로 바꾸고, 트랙을 JS/TS·관계형 DB·백엔드·IT 인프라·네트워크·MCP로 다시 짠다

- 상태: 일부 대체됨(0025: 2절의 프론트 심화 제외와 운영 개념 제외)
- 날짜: 2026-10-17
- ADR-0021의 1절(학습 트랙과 가중치)을 대체한다. 2~5절(상황 판단형 문제, 판단 사례, 게이트, 검토)은 그대로다.

## 맥락

ADR-0021의 시드 개념 256개는 Notion `복습` 문서에서 뽑았다. 맥미니 Claude Desktop에서 실제로 튜터링해 보니 세 가지가 맞지 않았다.

1. **이미 다뤄 본 것만 있다.** 복습 문서에서 뽑았으므로 앞으로 배우고 싶은 주제(JS 생태계 도구, 운영체제 등)는 매칭되는 개념이 없어 학습 맥락에 연결되지 않는다.
2. **개념 단위가 고르지 않다.** 업무 사례에서 나온 좁은 개념("프록시 자기 호출 함정", "nginx 설정 상속")과 넓은 개념이 섞여, 관련 개념과 선수 개념이 어색하게 나온다.
3. **우선순위가 다르다.** 지금 1순위는 면접보다 지금 업무 실력이다. 목표는 넷이다.
   - JS/TS: 언어를 깊이 이해해 코드를 빨리 읽고 리뷰하고 코딩테스트에 대비한다. JS 생태계(모듈, npm 같은 도구)가 왜 생겼고 새 도구가 어떤 장단점과 동작 원리를 갖는지 이해해 도구를 잘 쓰는 개발자가 된다.
   - 관계형 DB: 가장 널리 쓰이는 DB라서. 데이터 모델링, ERD 설계, 실무 정규화, 쿼리 최적화, DB 작동 방식을 깊이 안다.
   - 백엔드: 지금 쓰는 NestJS와 앞으로 실무에서 자주 만날 Spring의 작동 방식과 사용법을 안다.
   - IT 인프라: 인프런 "Docker가 쉬워지는 운영체제 이야기"(널널한 개발자) 강의 내용으로 구성한다.
   - MCP와 이 서버 설계: MCP 스펙과 모델이 도구를 쓰는 방식, 이 서버의 설계 결정과 대안을 이해해 기능 추가·성능 개선 지점을 스스로 찾는다.

## 결정

### 1. 시드는 커리큘럼이다

시드 YAML에는 앞으로 배울 것을 둔다. 이미 아는 것은 학습 기록과 수집(경험 카드)이 채운다. 시드 개념에 "이미 앎·배울 것" 같은 상태는 두지 않는다. 얼마나 아는지는 숙련도(설계 8장)가 잰다.

### 2. 학습 트랙

| 트랙 (키) | 가중치 | 범위 |
|---|---|---|
| JS/TS (`js`) | 0.2 | 언어(값·스코프·비동기·타입 시스템), JS 생태계(모듈 시스템, 패키지 매니저, 번들러·트랜스파일러·개발 서버, 런타임) |
| 관계형 DB (`database`) | 0.2 | 데이터 모델링·ERD·정규화, SQL, 인덱스와 쿼리 최적화, 트랜잭션과 동시성, DB 내부 구조(PostgreSQL 기준) |
| 백엔드 (`backend`) | 0.2 | 두 프레임워크에 공통인 서버 설계(DI, 계층, 요청 처리, 인증, 트랜잭션 관리, ORM, 캐시, 테스트), NestJS, Spring(컨테이너, AOP, MVC, Security, JPA) |
| IT 인프라 (`infra`) | 0.2 | 위 강의 커리큘럼 순서: 하드웨어 → 프로세스 → 파일 시스템 → 가상 메모리 → Overlay·Namespace·cgroups → 컨테이너 → NAT·netfilter → Docker |
| 네트워크 (`network`) | 0.2 | 웹 서비스가 통신하는 원리: IP·TCP·UDP·소켓·DNS, HTTP(메서드, 상태 코드, 캐싱, 쿠키, CORS, 버전), TLS, 프록시·CDN |
| MCP와 이 서버 설계 (`mcp`) | 0.2 | MCP 프로토콜(수명주기, 전송, 도구·결과·주석, 리소스, 원격·인증, MCP Apps, 보안), 모델의 도구 사용(호출 루프, 컨텍스트 비용, 도구 설명), 이 서버의 설계 결정과 트레이드오프, 확장·성능 개선 지점 |

- 가중치는 상대 비율이고 같게 두고 써 보며 조정한다. 쓰이는 곳은 ADR-0021과 같다(새 개념을 고를 때만).
- 프론트 심화(React, TanStack Query 등), CS 기초, 취업·면접 트랙은 없앤다. CS 기초 중 네트워크는 네트워크 트랙, OS는 IT 인프라, DB 이론은 관계형 DB로 옮겼다. 서술형 면접 연습을 만들 때 설명 능력 트랙을 다시 정한다.
- 경계: 네트워크는 "프로토콜이 어떻게 동작하나", IT 인프라는 "리눅스에서 어떻게 구성되고 진단하나"를 맡는다. 예를 들어 IP 주소·TCP는 네트워크, NAT·netfilter·`ss`·`tcpdump`는 IT 인프라다. 트랙에 걸친 관계는 ADR-0021처럼 `PREREQUISITE`·`RELATED` 간선으로 잇는다.
- 코딩테스트(자료구조·알고리즘)는 다루지 않는다. 객관식·빈칸보다 직접 코드를 짜서 풀어 보는 편이 효과적이기 때문이다. 코딩 문제 풀이 기능이 생기면 다시 정한다.
- MCP 트랙의 이 서버 설계 개념은 "이렇게 하지 않고 다르게 할 수는 없었나"를 묻는 트레이드오프 문제로 낸다. 정답의 근거는 ADR과 코드다. 설계가 바뀌면 ADR을 따라 개념 설명도 고친다.
- 이전 IT 인프라의 nginx, CI/CD, 인증서 발급, SSH 키 같은 운영 개념은 강의 범위 밖이라 뺐다.

### 3. 개념 크기

개념 하나는 강의 한 편이나 책 한 절 정도로 잡는다(예: "가상 주소와 페이징", "Copy on Write", "실행계획 읽기"). 세부 키워드(TDZ, `ON CONFLICT`, `veth`)는 별칭과 설명에 넣는다. 트랙마다 20~40개, 모두 193개다.

### 4. Notion 경험은 이 개념에 연결해 출제한다

2단계 수집에서 경험 카드와 판단 사례의 연결 개념을 이 목록에서 고른다. 그러면 업무 경험으로 만든 상황 판단형 문제(ADR-0021)가 이 커리큘럼 개념의 문제가 된다. 어느 개념에도 맞지 않는 경험은 개념 승인 정책(설계 6장)대로 새 개념을 제안한다.

### 5. 시드 적재는 시드에서 빠진 것을 지운다

시드가 커리큘럼이므로 YAML이 기준이다. 적재할 때 YAML에서 빠진 시드 개념(`origin = SEED`)과 그 관계, 빠진 트랙을 지운다. 수집·대화에서 생긴 개념은 남긴다. 학습 기록이 연결된 개념을 지우려 하면 외래 키 오류로 적재 전체가 취소되므로, 그때는 YAML에 남기거나 다른 개념으로 합칠지 정한다.

## 결과

- 좋은 점
  - 배우고 싶은 주제를 꺼내면 학습 맥락에 관련 개념과 선수 개념이 나온다.
  - 개념 크기가 고르게 되어 숙련도와 약점이 읽기 쉽다. 강의 순서와 선수 관계가 맞아 다음에 배울 개념을 고르기 쉽다.
  - YAML을 고치면 DB가 그대로 따라온다.
- 나쁜 점·감수할 것
  - Notion 경험 중 이 범위 밖의 것(GIS·PostGIS, React·TanStack Query, CI/CD, nginx)은 맞는 개념이 없다. 수집 때 새 개념 제안이 늘거나 연결되지 않는다.
  - 개념 수가 줄어 세부 주제의 숙련도는 개념 하나로 뭉쳐진다. 필요하면 수집·대화에서 하위 개념이 붙는다.
  - 업무 경험이 많은 영역(프론트)이 학습 목표에서 빠져, 면접에서 그 경험을 설명하는 연습은 서술형을 만들 때까지 미뤄진다.

## 검토한 대안

- **이미 아는 것과 배울 것을 함께 두고 상태로 구분:** 지난 경험과 연결은 쉽지만, 사용자가 시드는 커리큘럼이어야 한다고 정했다. 아는 정도는 숙련도가 따로 잰다.
- **프론트 심화 트랙 유지:** 업무 경험과 맞지만 지금 학습 목표에 없다.
- **코딩테스트를 JS/TS 안이나 별도 트랙으로:** 알고리즘 유형을 개념으로 두고 객관식으로 물을 수 있지만, 실제 풀이 능력은 코드를 짜 봐야 는다.
- **시드에서 빠진 개념을 DB에 남기기(기존 방식):** 지운 개념이 학습 맥락에 계속 나와 YAML과 DB가 어긋난다.
