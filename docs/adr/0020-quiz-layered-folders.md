# ADR-0020: quiz 모듈에서 레이어 폴더 구조를 먼저 시도한다

- 상태: 채택
- 날짜: 2026-10-15

## 맥락

ADR-0015는 기능 모듈 안에 도메인 규칙, 테이블 정의, 저장소, 유스케이스를 파일 이름 접미사(`*.schema.ts`, `*.repository.ts`, `*.service.ts`)로 구분해 한 폴더에 두고, 외부 기술에 붙는 입력 어댑터만 `mcp/`·`discord/` 폴더로 나눴다. 지금 모듈은 파일이 1~5개라 이 구조로 충분하다.

사용자는 이 프로젝트로 백엔드를 배우고 있고, NestJS 예제와 실무 코드에서 흔히 보는 레이어 폴더 구조(도메인 / 애플리케이션 / 인프라 / 표현)를 직접 써 보고 싶어 한다. 3단계의 `quiz` 모듈은 출제, 검증, 채점, 변형 문제, 문제 피드백이 들어가 파일이 가장 많아질 모듈이라, 레이어를 나눴을 때의 장단점을 확인하기에 알맞다.

## 결정

`tutor/quiz` 모듈 하나에서만 모듈 안 레이어 폴더를 쓴다. 다른 모듈은 ADR-0015 구조를 유지한다.

```
src/tutor/quiz/
├── quiz.module.ts
├── domain/          # 도메인 타입과 규칙(순수 함수): 문제, 채점, 변형 규칙. 다른 레이어와 외부 라이브러리를 모른다
├── application/     # 유스케이스(서비스)와 출력 포트. domain에만 의존한다
├── infrastructure/  # 테이블 정의(*.schema.ts), Drizzle 저장소, 프롬프트
└── presentation/
    └── mcp/         # MCP 도구 처리기 (입력 어댑터)
```

- **의존 방향:** presentation → application → domain, infrastructure → application·domain. domain은 아무 레이어도 import하지 않는다. ESLint `no-restricted-imports`를 폴더별로 걸어 강제한다.
- **저장소:** ADR-0015처럼 저장소 인터페이스를 따로 두지 않고 Testcontainers로 테스트한다. 테스트에서 가짜로 바꿔야 하는 외부 시스템(`ClaudeClient`)만 포트로 둔다. 레이어를 나눈다고 포트를 늘리지 않는다.
- **평가:** 3단계를 마치면 파일 찾기, 기능 하나를 고칠 때 오간 폴더 수, 린트 규칙이 잡아 준 실수를 돌아보고, 다른 모듈로 넓힐지 ADR-0015 구조로 되돌릴지 새 ADR로 정한다.

ADR-0015의 "기능별 Nest 모듈" 원칙과 포트·어댑터 범위는 그대로이고, `quiz` 모듈 안의 파일 배치만 다르다.

## 결과

- 좋은 점
  - NestJS 실무에서 흔한 구조를 직접 써 보며 레이어 분리의 효과와 비용을 비교한다.
  - 의존 방향을 폴더 단위 린트로 강제해, 채점 규칙이 Drizzle이나 MCP SDK에 닿는 실수를 리뷰 전에 잡는다.
  - 모듈 하나에서만 시도하므로 되돌리는 비용이 작다.
- 나쁜 점·감수할 것
  - 모듈마다 구조가 달라 처음 보는 사람이 헷갈릴 수 있다. `CLAUDE.md`에 예외로 적는다.
  - 파일 수가 적은 레이어는 폴더 하나에 파일 하나뿐인 깊이만 늘어날 수 있다.
  - 기능 하나를 고칠 때 여러 폴더를 오가야 한다(ADR-0013이 계층별 패키지를 뺀 이유와 같다). 모듈 안으로 범위를 좁혀 영향을 줄인다.

## 검토한 대안

- 지금 모든 모듈에 레이어 폴더 적용: 파일이 1~5개인 모듈에서는 깊이만 늘고 효과를 확인하기 어렵다.
- ADR-0015 구조 유지: 가장 단순하지만, 레이어 구조를 직접 써 보려는 학습 목적을 채우지 못한다.
- 전역 계층 패키지(`src/domain`, `src/infrastructure` …): ADR-0013에서 기능 하나를 고칠 때 여러 폴더를 오가야 해서 뺐다.
