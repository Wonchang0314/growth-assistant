# ADR-0029: 객관식·빈칸은 Sonnet이 쓰고 Opus가 정답을 모른 채 풀어 검증하며, quiz 레이어는 저장소·출제 어댑터를 포트로 둔다

- 상태: 채택
- 날짜: 2026-10-18
- 설계 문서 13장의 "출제·채점용 Claude 모델"을 정한다. ADR-0020의 "저장소 인터페이스를 따로 두지 않는다"를 `quiz` 모듈에서 바꾼다. 나머지(레이어 폴더, 의존 방향, 폴더별 린트, 3단계 끝 평가)는 그대로다.

## 맥락

3단계에서 `tutor/quiz`에 객관식·빈칸 출제와 검증을 만들었다(설계 문서 7.3). 정할 것이 셋이었다.

1. **모델과 검증 방식.** 설계는 "생성한 직후 별도 Claude 호출로 확인한다: 정답이 하나뿐인지, 정답이 보기 안에 있는지, 허용 답이 맞는 표기를 모두 담는지, 기준 자료만으로 풀 수 있는지"라고만 적었다. 판단 사례(ADR-0024·0026)에서는 Sonnet이 쓰고 Opus가 정답을 모른 채 풀어 보는 방식이 효과가 있었다(정답이 둘인 사례, 보기 모양으로 답이 보이는 사례를 잡았다).
2. **레이어와 포트.** ADR-0020은 의존 방향을 `presentation → application → domain`, `infrastructure → application·domain`으로 정하면서 "저장소 인터페이스를 따로 두지 않는다"고 했다. 그런데 출제 유스케이스(application)가 저장소와 프롬프트(infrastructure)를 직접 부르면 application → infrastructure가 되어 방향이 깨진다. 둘 중 하나를 바꿔야 한다.
3. **약점 재료.** 설계는 출제 프롬프트에 최근 오개념(`quiz_attempt.misconception`), 빈칸 오답, 학습 기록의 헷갈린 점, 경험 카드의 실수를 넣는다고 했다. 풀이 기록(`quiz_attempt`)은 채점 도구와 함께 만든다.

## 결정

### 1. 출제와 검증

| 단계 | 하는 것 |
|---|---|
| 출제 (`QUIZ_GENERATION`, Sonnet) | 개념(설명, 상위·선수 개념), 유형, 이미 낸 핵심, 학습 기록의 헷갈린 점, 관련 경험 카드 3장, 출제 지침을 넣는다. 웹 검색은 쓰지 않는다 |
| 모양 검사 (코드) | 객관식: 보기 4개, 같은 보기 없음, 정답 보기 하나(오개념 null)가 `answer`와 같음, 오답마다 오개념, 정답만 긴 보기(1.5배, 판단 사례와 같은 게이트). 빈칸: `____` 정확히 하나, 문장에 정답이 드러나지 않음. 둘 다: 패턴 게이트(ADR-0024, `UPPER_SNAKE`·IP·URL·도메인) |
| 보기 섞기 (코드) | 생성 모델이 정답을 앞쪽에 두는 버릇(판단 사례 재시험 7장 중 5장)을 지운다 |
| 검증 (`QUIZ_VERIFICATION`, Opus) | 문제와 보기만 보여 주고(정답 표시·오개념·해설·근거 없음) 풀게 한다. 고른 답이 정답과 같고(빈칸은 정답·허용 답과 표기 차이를 빼고 같고), 정답이 하나로 정해지며, 검토자가 문제를 말하지 않아야 통과다 |

- 걸리면 이유를 붙여 1회 다시 쓴다. 그래도 걸리면 `INVALID`로 저장하고 이유를 `validation_note`에 남긴다(설계 5.4에 컬럼 추가). `VALID`만 출제에 쓴다.
- 빈칸 검토자가 다른 표기로 맞게 답하면 걸린 이유에 "맞는 표기면 acceptedAnswers에 넣어라"를 적어, 다시 쓸 때 허용 답이 채워진다. 설계의 "허용 답이 맞는 표기를 모두 담는지"를 이렇게 확인한다.
- "기준 자료만으로 풀 수 있는지"는 따로 보지 않는다. 기준 자료를 함께 주면 검토자가 답을 베끼게 되고, 빼면 일반 지식으로 풀 수 있는지만 본다. 개념 문제는 일반 지식으로 풀려야 하므로 후자를 택했다.
- `npm run quiz -- --concept <이름>`으로 개념 하나의 문제를 만들어 출력한다. 출제 품질을 보는 수단이다(설계 10장의 수동 평가). 문제 풀 보충과 즉석 생성은 `get_review_set`과 함께 붙인다.

### 2. quiz 레이어의 출력 포트

- `application/ports.ts`에 `QuizQuestionRepository`(저장소)와 `QuestionGenerator`(출제·풀이 LLM 어댑터)를 추상 클래스로 두고, `infrastructure`가 구현한다(`DrizzleQuizQuestionRepository`, `ClaudeQuestionGenerator`). 모듈이 `{ provide: 포트, useClass: 구현 }`으로 잇는다.
- 프롬프트와 응답 스키마(zod)는 `infrastructure`에 둔다(ADR-0020 그대로). application은 zod와 Drizzle을 모른다.
- 다른 모듈의 서비스(`ConceptService`, `StudyNoteService`, `ExperienceRepository`, `AppSettingRepository`)는 포트 없이 application에서 직접 쓴다. 레이어 규칙은 `quiz` 안의 폴더에만 걸린다.
- 폴더별 린트(`eslint.config.js`의 `quizLayer`)로 방향을 강제한다. domain은 다른 레이어와 Nest·Drizzle·zod·MCP SDK를, application은 infrastructure·presentation과 Drizzle·MCP SDK를, infrastructure는 presentation을 import하지 못한다.
- 여러 레이어를 함께 쓰는 통합 테스트(`quiz-generation.db.spec.ts`)는 레이어 폴더 밖, 모듈 루트에 둔다.

### 3. 약점 재료는 있는 것부터

- 지금은 학습 기록의 헷갈린 점(그 개념에 연결된 최근 기록 5개)과 경험 카드(실수·원인)만 넣는다. 오답 오개념과 빈칸 오답은 `quiz_attempt`를 만드는 채점 작업에서 더한다.

## 결과

- 좋은 점
  - 정답이 둘이거나 보기 모양으로 답이 보이는 문제를 사람이 보기 전에 거른다. 채점은 계속 코드가 결정적으로 한다.
  - 레이어 방향이 린트로 지켜진다. 출제 흐름(application)이 Drizzle·zod·`claude` CLI를 모른다.
  - 출제 지침을 대화에서 고치면 다음 문제부터 반영된다(`update_quiz_guideline`, 재배포 없음).
- 나쁜 점·감수할 것
  - 문제 하나에 `claude -p`를 2~4번 부르고, Opus 검증이 가장 느리다. 즉석 생성은 수십 초 이상 걸린다(설계 7.3에서 감수하기로 함). 문제 풀 보충(4단계)이 생기면 줄어든다.
  - ADR-0020이 피하려던 포트가 둘 생겼다. 레이어를 나눈 대가이고, 3단계 끝 평가에서 함께 본다.
  - 사실 오류는 Opus가 풀면서 알아챌 때만 걸린다. 평가 세트와 `report_question`(채점 작업)으로 보완한다.
  - 웹 검색을 쓰지 않아 최신 버전 동작은 문제로 내기 어렵다. 출제 프롬프트가 버전에 따라 다른 동작은 조건을 밝히거나 피하게 한다.

## 검토한 대안

- **같은 모델(Sonnet)로 검증:** 싸고 빠르지만, 같은 모델이 자기 문제의 빈틈을 놓치기 쉽다. 판단 사례에서 Opus 검증이 걸러낸 경험을 따른다.
- **정답을 주고 "맞는지" 확인시키기:** 한 번에 끝나지만, 정답을 알면 다른 보기도 맞을 수 있다는 점을 덜 본다. 판단 사례의 정답 숨김 검증을 따른다.
- **application이 infrastructure를 직접 부르기(ADR-0020 문구 그대로):** 포트가 없어 단순하지만 의존 방향이 일반 3계층처럼 바뀌어, 레이어 구조를 써 보려던 목적(ADR-0020)과 맞지 않는다.
- **`quiz_attempt`를 지금 만들기:** 채점 도구 없이 쓰는 곳이 없다.
