# ADR-0033: 출제에 웹 검색을 쓰고, 근본 원인은 약점 둘 이상이 기댈 때만 고르며, 상황 판단형은 개념 문제 둘마다 하나 내고, 빈칸은 복습에서 뺀다

- 상태: 일부 대체됨 (3절 상황 판단형 비율 → ADR-0038)
- 날짜: 2026-10-18
- ADR-0029 1절의 "웹 검색은 쓰지 않는다", ADR-0031의 근본 원인 후보 조건, ADR-0032 1절의 "개념 문제와 번갈아"를 바꾼다. 나머지는 그대로다.

## 맥락

3단계 출제·복습 도구를 배포한 뒤 `npm run quiz`로 개념 몇 개(서버 캐시, SQL NULL과 3값 논리, 인덱스 원리, cgroups)를 시험했다(2026-10-18). 문제 9개 중 VALID는 3개였다. 걸린 이유 중 하나는 제품·엔진·버전에 따라 갈리는 동작에 조건이 없는 것이었다. 예: 커밋 전 캐시 재적재는 MVCC인 DB에서만 성립하고, 인덱스 갱신 비용은 InnoDB change buffer에 따라 달라진다. 이런 사실은 일반 지식만으로는 확인하기 어렵다.

같은 때 3단계 PR의 열린 질문(ADR-0030·0031·0032)을 사용자에게 물었다.

## 결정

1. **출제에 웹 검색을 쓴다.** `QUIZ_GENERATION`에 `WebSearch`·`WebFetch`를 허용하고 타임아웃을 3분에서 5분으로 늘린다. 프롬프트는 제품·엔진·버전·설정에 따라 갈리는 사실만 검색으로 확인하고, 문제에 그 조건을 밝히고, 확인한 문서 주소를 기준 자료에 적게 한다. 일반 원칙만으로 정해지는 문제는 검색하지 않는다. 대화 중 즉석 생성과 `npm run quiz`, 4단계 예약 작업 모두 같다(사용자 결정). 검증(`QUIZ_VERIFICATION`)은 그대로 웹 없이 정답을 모른 채 푼다.
2. **근본 원인 후보는 약점 개념 둘 이상이 기대는 선수 개념만이다.** 근본 원인은 여러 약점의 공통 원인이라는 뜻에 맞추고, 출제 맨 앞자리를 덜 차지하게 한다. 약점 하나만 기대는 선수 개념은 학습 맥락의 "약한 선수 개념"으로 보여 줄 수 있지만 근본 원인으로 올리지 않는다.
3. **상황 판단형은 개념 문제 둘마다 하나 낸다.** 개념에 새 문제를 만들 때, 아직 상황 판단형이 없거나 마지막 상황 판단형 뒤로 개념 문제가 두 개 나왔으면 상황 판단형 차례다(흔들린 문제의 변형이 먼저인 것은 그대로). 개념 문제 차례에는 상황 판단형의 변형도 고르지 않는다. 원리 확인을 더 자주 하고, 긴 상황 판단형 문제의 피로를 줄인다.

4. **빈칸 문제는 복습에서 뺀다.** 시험한 빈칸 12개 중 VALID가 3개였고, 걸린 이유가 반복됐다(용어 이름만 묻기, 다른 용어도 들어감, 엔진·근사 조건 부족). 사용자가 다시 넣을지 나중에 정하기로 했다. 복습에서 만들고 내는 유형을 `ENABLED_TYPES`(지금은 객관식만) 한 곳에 두고, 뒤에서 만들기·문제 고르기·`npm run quiz` 기본값이 이것을 쓴다. 이미 있는 빈칸 문제와 채점·검증 코드는 남겨 두고, `npm run quiz -- --type FILL_BLANK`로는 계속 만들어 볼 수 있다. 빈칸 게이트의 "정답이 문장에 드러남" 검사는 숫자 답이면 건너뛴다("4코어"의 4와 계산한 답 4를 글자로는 구분할 수 없어 풀이 검증에 맡긴다).

그대로 두는 것(사용자 결정):

- 새 개념(대화에서 다룬 적 없는 개념)은 우선순위 ①②로 채우고 남은 하루 상한을 모두 채운다(ADR-0030).
- 검증에 걸리면 다시 쓰는 것은 한 번이다(ADR-0029). 대신 시험에서 반복된 실패(단정 표현, 결론이 혼자 다른 정답, 답을 알려 주는 조건, 조합형 보기의 다수결 단서, 용어 이름만 묻는 빈칸, 엔진·근사 조건)를 프롬프트 규칙으로 더한다.

## 결과

- 좋은 점
  - 엔진·버전 조건이 빠져 걸리는 문제가 줄고, 기준 자료에 출처가 남는다.
  - 근본 원인 후보가 여러 약점을 한꺼번에 풀 수 있는 개념으로 좁혀진다.
- 나쁜 점·감수할 것
  - 검색한 문제는 출제가 더 오래 걸리고 사용량이 는다. 대화 중 즉석 생성은 뒤에서 하므로(ADR-0030) 기다림은 "만드는 중"이 길어지는 것으로 나타난다.
  - 검색 결과가 틀리거나 오래된 문서일 수 있다. 검증은 웹 없이 일반 지식으로 풀어 맞는지 보므로 검색으로만 확인되는 세부는 검증이 정답을 못 고를 수 있다.
  - 약점이 하나뿐인 초기에는 근본 원인 후보가 없다.

## 검토한 대안

- **웹 검색은 4단계 예약 작업에서만:** 대화 중 생성이 빠르지만, 지금 쓰는 문제 품질이 그대로다. 사용자가 지금부터 켜기로 했다.
- **다시 쓰기를 두 번으로:** VALID 비율이 오르지만 걸리는 문제의 호출이 늘어난다. 사용자는 프롬프트를 먼저 다듬기로 했다.
- **상황 판단형 1:1 그대로, 또는 상황 판단형 우선:** 판단 사례를 빨리 쓰지만 원리 확인이 줄어든다.
